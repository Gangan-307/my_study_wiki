## 二、不定项选择题（多选、错选、漏选均不得分；每题 4 分，共 12 分）

**A2-1.** 关于 `memcpy` 与 `memmove`，说法正确的有？

A. `memcpy` 不保证在源和目标内存重叠时正确工作，重叠时应使用 `memmove`
B. 读写寄存器时用 `(volatile uint32_t *)` 强制转换后直接访问，这条路径**不存在**"源和目标重叠"的问题
C. `memmove` 在源和目标重叠时会正确处理，但具体按什么方向拷贝由实现决定，标准不做保证
D. `memcpy(dst, src, n)` 在拷贝完成后会自动在 `dst` 末尾补 `'\0'`

**A2-2.** 某 Cortex-M 工程用 DMA + "半传输/传输完成"双中断接收串口数据，现场偶发"帧长度正确，但负载整体错位一两个字节"。下列可能的原因有？

A. ISR 里把 DMA 缓冲区的字节搬进环形缓冲区，但主循环消费时**读/写索引没有做原子处理或临界区保护**
B. 环形缓冲区的 `head` 在 ISR 与主循环里都会被修改，两边都没有关中断
C. 接收方只按"已收到的字节数"判断帧结束，而协议本身没有帧头/长度/校验来定界
D. 只要把 `memcpy` 换成 `memcpy_s` 并检查返回值，就能解决这个问题

**A2-3.** 关于 MMU / MPU，说法正确的有？

A. MMU 的主要作用之一是**虚拟地址到物理地址的转换**
B. 32 位 Linux 系统中每个进程的虚拟地址空间通常约 4 GB
C. 开启 MPU 后，可以把某个区域的访问权限设为"不可执行"，用于防止跑飞
D. MMU 的主要作用是加快 CPU 主频

**B1-1.** 关于进程与线程，说法**错误**的是？

## 二、不定项选择题（每题 4 分，共 12 分）

**B2-1.** 关于 `epoll`、`select`、`poll` 的说法正确的有？

A. `select` 支持的 fd 数受限（通常 `FD_SETSIZE` = 1024）
B. `epoll` 的边缘触发（ET）模式下必须**一次性读干净**，否则可能不再收到通知
C. `poll` 用数组管理 fd，不再有 `FD_SETSIZE` 限制
D. `epoll` 的 `EPOLLIN` 一定意味着"已经收到了一条完整的应用层消息"

**B2-2.** TCP 是面向字节流的，**应用层**要正确拿到一条消息，说法正确的有？

A. 一次 `recv` 可能只返回半条消息，也可能返回"一条半"
B. "粘包/半包"不是 TCP 的缺陷，而是字节流模型决定的
C. 用 `write` 一次发出的报文，`recv` 对端一定能一次收到
D. 应用层协议应定义**长度字段**或**分隔符 + 校验**来定界

**B2-3.** 死锁的四个必要条件，正确的有？

A. 互斥条件：资源一次只能被一个进程占有
B. 请求并保持：已占有的资源不释放，又去请求新资源
C. 不可剥夺：已分配的资源不能被强行抢占
D. 循环等待：存在进程—资源环形等待链
E. 只要打破了其中**任意一个**必要条件，就不可能发生死锁

# 参考答案与解析

> 标记说明：**【实测】** = 用 `gcc 15.2.0 (x86_64)` 编译运行核对过输出；**【ABI】** = 按目标平台 ABI 规范推导（本机没有 32 位运行库，无法实际链接运行）。

## 卷 A 答案

**A1-1 → C。**【实测，x86_64 上同口径】
`struct S`：`a` 偏移 0；`b` 需要 4 字节对齐 → 偏移 4，填充 3 字节；`c` 偏移 8~9；整体按最大成员 4 对齐 → 补到 12。所以第一项是 12（A、D 排除）。

第二项才是真正的坑：`u` 是 `unsigned int`，`-1` 在 `u > -1` 中被转换成 `unsigned`，变成 `0xFFFFFFFF`，所以 `3 > 0xFFFFFFFF` 为**假** → `0`。**有符号数与无符号数比较时，有符号数会先被转换到无符号类型**；这也是 `for (unsigned i = n - 1; i >= 0; i--)` 为什么是死循环的根源。
复习：[C 语言易错题](/embedded-interview/c-basics.md)、[类型与转换](/c-language/types-and-conversions.md)、[结构体专题](/c-language/struct.md)、[更早年份对照卷的 `pack` 题](/embedded-interview/hikvision-earlier-papers.md)

**A1-2 → A。**【ABI：32 位下 `int` 为 4 字节】
- ① `p[7]` 等价于 `*(p + 7)`，`int *` 步长为 4 字节 → 从 `&data[5]` 前进 7 个元素 → `data[12] = 13`。
- ② 与 ① 完全等价 → `13`。
- ③ `*p * 2 + 7`：`*` 优先级高于 `*`（乘法）？——**注意这里有两个 `*`**：一元 `*p` 是解引用，与乘法 `* 2` 并存时**一元运算符优先级更高**，所以是 `(*p) * 2 + 7 = 6 * 2 + 7 = 19`。如果错看成 `*(p * 2 + 7)`，会算成 `data[19]`——**越界**，这就是本题的陷阱。

真正的区分点在 ③：`*p + 7`（加）与 `*p * 2 + 7`（乘）看起来很接近，但一个得到 13、一个得到 19。考场上请先**标出运算符优先级**再算。
真题同款：[P1-Q02](/embedded-interview/hikvision-written-test.md#p1q02)。
复习：[指针专题](/c-language/pointer.md)、[数组专题](/c-language/arrays.md)、[运算符专题](/c-language/operators.md)

**A1-3 → A。** 口诀：**`const` 修饰 `*` 左边的内容** → ① `const char *p1` = 指向常量的指针（指针可变、内容不可改）；② `char * const p2` = 常量指针（指针不可变、内容可改）；③ 两者都不可变。
复习：[2019 应用岗考点"指针常量和常量指针"](/embedded-interview/hikvision-written-test.md)、[指针专题](/c-language/pointer.md)

**A1-4 → B（3）。**【实测输出：`c = 3`，`a = 2`】
宏**文本展开**后是 `((++a) > (b) ? (++a) : (b))`。求值顺序：
1. 先算条件 `(++a) > (b)`：`++a` 让 `a` 从 1 变成 **2**，`2 > 3` 为**假**——注意**这里 `a` 已经被自增了一次**；
2. 条件为假，走 `:` 后面的分支，取 `b = 3`，所以 `c = 3`（若条件为真才走 `(++a)`，那时 `a` 会再涨一次）。

所以本题选 **B**。真正要记住的是：**结果是 3，但 `a` 已经被改了**——宏的参数**被求值了一次**，而调用者很可能以为 `MAX` 不会动自己的变量。若写成 `MAX(a++, a++)`，同一个参数被求值两次，且无序列点，才是**未定义行为**。

工程结论：宏参数不保证"只求值一次、无副作用"，带副作用的实参（`i++`、`func()`）要么避免传入，要么改用 `static inline` 函数。真题同款：[P1-Q13 不带括号的带参宏](/embedded-interview/hikvision-written-test.md#p1q13)、[P4-5 带参宏综合计算](/embedded-interview/hikvision-written-test.md#p4q5)。
复习：[预处理、编译与链接](/c-language/preprocess-build-link.md)

**A4-1 参考答案（12 分）**

1. （3 分）

   - 加了 `volatile` 后，编译器**不能**把访问缓存到寄存器、不能合并、不能删除，因此每次循环都会真的去读内存 → 这个"等待"才成立。
   - 但要注意：`volatile` **只规定访问不能被优化掉**，它不产生内存屏障，也不保证原子性；它解决的是"**可见性**"，不是"**一致性**"。
2. （4 分）**读—改—写不是原子操作。** `g_rx_cnt++` 在汇编层是"读 → 加 1 → 写回"三步：
   - **8 位 MCU（如 STM32F103）**：`volatile uint32_t` 的 `++` 是"四次字节读 → 四次字节写"或"32 位加载 → 加 → 存"，**在"加"和"存"之间可能被中断打断**。若 ISR 此时也改同一个变量，主循环写回时会覆盖 ISR 的递增，**丢一次计数**。
   - **32 位 MCU 上的 `uint32_t`**：单条 `LDR`/`STR` 对齐访问本身不会被打断（对齐的 32 位访问是原子的），所以"只读一次"或"只写一次"是安全的；但 **`++` 仍是三步**，仍然不原子。如果改成 `uint8_t`，某些编译出来的"读—改—写"更明显（RMW 指令被打断时也会丢更新）。
   - 结论：**写入只有一个"写者"（ISR）时**，主循环读单个 32 位对齐变量、ISR 写它，通常安全；**一旦存在"多个写者"或"读写都要改"**，就必须用临界区（`taskENTER_CRITICAL()` / 关中断）或原子操作。
3. （5 分）**只靠 `volatile` 传递数据会出问题**，因为：
   - **顺序问题**：生产者先写数据、后写"写指针"（或有效标志），但编译器和 CPU 都可能重排无关的存储访问——消费者一旦看到写指针更新，就可能读到**尚未写完的数据**。标准做法是 **生产者写完数据后用内存屏障（`atomic_thread_fence(memory_order_release)` / `__DMB()`）保证顺序，最后更新写指针**，或使用 C11 `atomic_uint` 的 `release`/`acquire`（在多核 SoC 上尤其关键）。
   - **多写者问题**：若 ISR 和任务都会改同一个标志/指针，`volatile` 挡不住"读—改—写"被打断（见第 2 问）。
   - **消费者可见性**：消费者读完数据、更新读指针后，必须让生产者"看到"读指针已推进，否则生产者会误判缓冲区已满。
   - 工程上最常用的是 **单生产者 + 单消费者（SPSC）无锁环形队列**：写指针只由生产者写、读指针只由消费者写，两侧用 `memory_order_release/acquire` 访问；需要多生产者时再加临界区或原子 CAS。
   - ISR 里**禁止**用阻塞 API，`xQueueSendFromISR` 才行——这是同一个"并发"问题在 RTOS 层的延伸。

   复习：[C05 volatile](/embedded-interview/c-basics.md#c05)、[ISR、并发与 volatile](/c-language/isr-concurrency.md)、[R05 为什么 ISR 要用 FromISR API](/embedded-interview/rtos.md#r05)、[R10 关中断/挂起调度器/加锁的区别](/embedded-interview/rtos.md#r10)

2. （4 分）**"显示端把高位字节吞掉/按 `signed char` 做扩展"** 的特征是：**每个字符的字节数一致（UTF-8 通常每个汉字 3 字节），但每个汉字都坏成相同的模式**；文本中乱码形如"若干字节变成同一个替换字符 `?`"或"每个汉字第一个字节变成 `?`"，而 ASCII 完全正常。

**A5-1 参考答案（16 分）**

```c
/* 长度用循环自算，避免把 NULL 直接送进库函数 strlen（NULL 与任意指针相减是未定义行为） */
size_t my_strlen(const char *s)
{
    const char *p = s;
    if (s == NULL)
        return 0;
    while (*p)
        p++;
    return (size_t)(p - s);
}

char *my_strcpy(char *dst, size_t dst_size, const char *src)
{
    size_t n;
    if (dst == NULL || src == NULL || dst_size == 0)
        return NULL;
    n = my_strlen(src);
    if (n + 1 > dst_size) {      /* n+1 而不是 n：要给 '\0' 留位置 */
        dst[0] = '\0';           /* 失败也保证目标串合法，不留半截脏数据 */
        return NULL;
    }
    memmove(dst, src, n + 1);    /* 重叠安全；n+1 把 '\0' 一起拷 */
    return dst;
}
```

关键得分点：
1. **`n + 1 > dst_size`**：很多人的写法是 `if (n > dst_size)`，恰好漏掉一个字节的边界——当 `n == dst_size` 时会写越界 1 字节。
2. **`memmove` 而不是 `memcpy`**：`src == dst` 或两者重叠时 `memcpy` 未定义；`strcpy(dst, dst)` 这种自拷贝在工程里确实会出现。
3. **失败路径也置 `dst[0] = '\0'`**：保证调用方后续 `printf("%s")` 不会读到旧垃圾。
4. `dst_size == 0` 时返回 `NULL`，绝不写任何字节。【实测】`"abc"→ok`；`src == dst` → ok；超长 → 拒绝。

第 2 问：`memcpy` 要求源和目标**不重叠**，否则行为未定义；`memmove` 允许重叠，内部会处理方向。本题入口允许"src 就是 dst"，或有重叠，所以必须用 `memmove`。

第 3 问（4 个用例，期望行为）：
1. `my_strcpy(dst, sizeof dst, "abc")` → 返回 `dst`，`dst == "abc"`；
2. `my_strcpy(dst, 4, "abcdef")` → 返回 `NULL`，`dst[0] == '\0'`，**无越界**；
3. `my_strcpy(dst, sizeof dst, dst)`（src == dst）→ 返回 `dst`，内容不变；
4. `my_strcpy(dst, 1, "")` → 返回 `dst` 且 `dst[0] == '\0'`（空串恰好能放进 1 字节）；
   补充：`my_strcpy(dst, 0, "a")` / `dst == NULL` / `src == NULL` → 返回 `NULL`。
   复习：[字符串与缓冲区](/c-language/strings-buffers.md)、[真题：手写 `strcpy`/`strcat`/`strcmp`/`strstr`](/embedded-interview/hikvision-written-test.md)

**A5-2 参考答案（14 分）**

```c
void bubble_sort(int *a, int n)
{
    if (a == NULL || n < 2)
        return;
    for (int i = 0; i < n - 1; i++) {
        int swapped = 0;
        for (int j = 0; j < n - 1 - i; j++) {
            if (a[j] > a[j + 1]) {     /* 严格大于才交换 => 相等元素不换位 => 稳定 */
                int t = a[j];
                a[j] = a[j + 1];
                a[j + 1] = t;
                swapped = 1;
            }
        }
        if (!swapped)
            break;                     /* 某一趟无交换：已有序 */
    }
}
```

【实测】`{4,1,4,2,1,3}` → `1 1 2 3 4 4`，且相同元素的相对顺序不变。

第 2 问：**最坏都是 O(n²)**。不带提前退出的冒泡，最坏与最好比较次数都是 `n(n-1)/2`，即 O(n²)；带上提前退出后，最好情况是 O(n)（第一趟就发现有序）。快排平均 O(n log n)，**数组已有序且每次取首/尾为基准时最坏 O(n²)**。
嵌入式场景：**快排更要注意最坏情况**——传感器、日志这类数据经常"接近有序"，容易踩到最坏；而且递归快排的**栈深度最坏是 O(n)**，在任务栈只有几百字节的 RTOS 里会栈溢出（见 [R08](/embedded-interview/rtos.md#r08)）。冒泡/插入都是"原地、常数栈"，不会因为数据形态爆栈。
（真题同款：[P1-Q01 冒泡与插入的最坏复杂度](/embedded-interview/hikvision-written-test.md#p1q01)、[P1-Q05 快排三种情况](/embedded-interview/hikvision-written-test.md#p1q05)、[P5-Q01 出栈序列](/embedded-interview/hikvision-written-test.md#p5q1)）

第 3 问：**选插入排序**（或带提前退出的冒泡）。理由：基本有序时插入排序的比较次数接近 O(n)，且没有递归栈开销；对 8 个元素这种小规模，算法本身的差距远小于代码体积和栈占用带来的风险。

**B4-1 参考答案（12 分）**

1. （6 分）
   - **现象根因**：**TCP 是字节流**，`recv()` 只保证"这次返回了若干个字节"，不保证"返回了一个完整帧"。把"`recv` 返回值当作已经读到的字节数"是很多现场 bug 的源头。
   - **正确流程**：累积缓冲 + 状态机。反复 `recv`，把字节追加进缓冲区；直到"累积 ≥ 2"才能解析长度字段，再继续累积到"≥ 2 + len"才取出整帧；`recv` 返回 0 表示对端关闭（本帧永远等不到了），返回 -1 且 `errno == EAGAIN/EWOULDBLOCK` 表示本轮读完（非阻塞或 ET 模式）。
   - **两个现场现象的成因**：
     - "长度解析成 65535"：长度字段被**错位解析**——例如把上一帧残留的 `0xFF` 当作长度高字节；
     - "负载乱码/整体错位"：同一连接上**前后两次处理留下残留**，或把半帧当整帧用了。
   - 一句话结论：**`recv` 的返回值是"这次拿到多少"，不是"我要多少"**；契约必须由**应用层协议**给出，不能由 TCP 给出。
2. （3 分）不依赖 `arpa/inet.h` 的打包：
   ```c
   static void put_be16(uint8_t *p, uint16_t v)
   {
       p[0] = (uint8_t)(v >> 8);   /* 大端：高字节在前 */
       p[1] = (uint8_t)(v & 0xFF);
   }
   static uint16_t get_be16(const uint8_t *p)
   {
       return (uint16_t)((p[0] << 8) | p[1]);
   }
   ```
   要点：**按位拼，不按内存布局拼**（与主机字节序无关）；`(uint16_t)` 强转必须加，否则 `uint8_t` 提升成 `int` 后左移 8 位在高字节场景下是合法的，但赋值回 `uint16_t` 时会截断——**显式转换是给读代码的人看的**。
3. （3 分）接收缓冲区设计：
   - **静态分配**固定大小的 `g_rx_buf`（如 2 KB，大于最大帧长），**不放在任务栈上**；或用 `malloc` 一次分配、全程复用；
   - **环形缓冲区**承接"字节流"（`rb_put` 由 `recv` 填），**解析器**在环形缓冲区里找帧头、读长度、等齐了再整帧拷进独立大缓冲区（避免"帧内两段不连续"）；
   - **长度上限校验**：`len > MAX_FRAME_LEN` 直接丢弃并计数，防止恶意/坏数据导致越界写；
   - 解析与接收解耦：`recv` 线程只负责"搬字节"，解析在独立任务或解析函数里做。

**B4-2 参考答案（14 分）**

1. （6 分）逐条判断：
   - **互斥**：L1、L2 都是同一时刻只能一个线程持有的锁 ✔
   - **请求并保持**：A 持有 L1 又去请求 L2 ✔（B 同理）
   - **不可剥夺**：POSIX 互斥锁没有"抢锁"语义，A 不释放 L1 就死等 L2 ✔
   - **循环等待**：A→L2（被 B 持有），B→L1（被 A 持有），形成环 ✔
   - 现场现象：CPU 占用不高但所有线程都卡住；用 `gdb` attach 后 `thread apply all bt` 能看到 A、B 都停在 `pthread_mutex_lock`，且互相等待的锁正好是对方案子。
2. （4 分）编码层预防（至少两条，说明为什么有效）：
   - **锁顺序统一**：全项目规定"先 L1 后 L2"，任何线程不得反序。→ 直接打破**循环等待**条件（环不可能形成）。
   - **一次只持一把锁，或缩小临界区**：持有 L1 时不做会申请 L2 的事（把申请提前或延后）。→ 破"请求并保持"。
   - **用 `pthread_mutex_trylock` + 超时 + 释放已持锁后重试**：抢不到就退还 L1，打破"不可剥夺"。
   - **把锁的生命周期绑定到资源/对象**（RAII 风格的 C 封装：`lock/unlock` 成对封装在函数里，用 `goto out` 统一出口）。
   - 注意：**只用"加超时"是不够的**——超时能让程序不退，但会引入重试风暴和更难查的时序 bug；它只能算"兜底"，不能算预防。
3. （4 分）收集证据再重启：
   ```sh
   # ① 优先保留现场：让进程转储 core（不要直接 kill -9）
   kill -ABRT <pid>                        # 触发 SIGABRT，按 /proc/sys/kernel/core_pattern 生成 core
   ls -l /proc/<pid>/cwd/core*             # 确认 core 落在哪
   ```
   - **shell 内置的 `kill` 只接受信号名/编号，不认 `-SIGABRT` 这种写法**：`kill -SIGABRT <pid>` 可能报错，稳妥写法是 `kill -ABRT <pid>` 或 `kill -6 <pid>`；`gcore <pid>` 是 gdb 的附加工具，要确认设备上装了 gdb 才能用。
   - **没有 gdb / 不能生成 core 时**：用 `cat /proc/<pid>/task/*/stack` 看每个线程在内核里卡在哪；`cat /proc/<pid>/task/*/wchan` 拿到等待点。用户态调用栈可以现场用 `pstack <pid>`（busybox 环境可能没有）。
   - **仍不够时**：重启前先抓"谁持有谁在等"——把 `pthread_mutex_lock/unlock` 包一层，记录 `(锁地址, 线程 id, 时间)` 到内存环形日志；卡死超时后把日志打印到串口，**再**重启。
   - 结论：**现场的"证据"比"重启恢复"值钱**，先拿 core / 栈 / 日志，再重启、再复现。

**B5-1 参考答案（14 分）**

```c
unsigned long long pow2(int n)
{
    if (n < 0)
        return 0;              /* 2 的负次方不是整数，返回 0 表示非法 */
    if (n == 0)
        return 1;              /* 递归出口：2^0 = 1 */
    return 2ULL * pow2(n - 1);
}
```

【实测：`pow2(0)=1`，`pow2(1)=2`，`pow2(63)=9223372036854775808`】
- **溢出**：结果放在 `unsigned long long`（64 位，最大 `2^64-1`）里，`2^63` = `0x8000000000000000` 仍能表示，**n = 63 是最大值**；`n ≥ 64` 时 `2^64` 回绕成 `0`。若用有符号 `long long`（最大 `2^63-1`），则 **n ≥ 63 就溢出**。判断：入口处直接 `if (n >= 64) return 0;`（用无符号）或 `if (n >= 63) return 0;`（用有符号）。
- **栈深度**：递归层数为 `n + 1` 层。每层至少要压入局部变量 + 返回地址（典型 ARM 4~16 字节，含对齐），也就是 `n` 增加时栈线性增长。
- **RTOS 任务栈**：推荐用 **迭代**——
  ```c
  unsigned long long pow2_iter(int n)
  {
      unsigned long long r = 1;
      if (n < 0 || n >= 64) return 0;
      for (int i = 0; i < n; i++)
          r <<= 1;
      return r;
  }
  ```
  一句话：**"递归能写"不等于"RTOS 里能这么写"**；任务栈是按 word/字节精确分配的（[R08](/embedded-interview/rtos.md#r08)），递归深度必须可控，否则用迭代或把递归改成尾递归并开优化。
- 若结果超 64 位（如 `2^200`，只要十进制文本）：用**大整数**表示——"以 10^9 为一段"的 `uint32_t` 数组（每个数组元素存 9 位十进制，`uint64_t` 中间结果不会溢出）。每次把整个数组乘 2、再从低位向高位处理进位；也可以直接"模拟十进制竖式"逐位乘 2。只需几十字节 RAM，适合 MCU。
  复杂度 O(n × 段数)，`2^200` 约 61 位十进制 → 7 个段，完全可以跑在 Cortex-M0 上。
  （真题同款：[P3-Q03 递归写 2 的 N 次方](/embedded-interview/hikvision-written-test.md#p3q3)）

**B5-2 参考答案（16 分）**

```c
/* 头尾哨兵：初始化后 head<->tail 互相指向，任何时刻"两边都有邻居"，
   插入/删除都不用判空指针 */
void list_init(DList *l)
{
    l->head = (DNode *)calloc(1, sizeof(DNode));
    l->tail = (DNode *)calloc(1, sizeof(DNode));
    l->head->prev = NULL;
    l->head->next = l->tail;
    l->tail->prev = l->head;
    l->tail->next = NULL;
}

DNode *list_node_new(int key, int value)
{
    DNode *n = (DNode *)malloc(sizeof(DNode));
    if (n == NULL)
        return NULL;
    n->prev = n->next = NULL;
    n->key = key;
    n->value = value;
    return n;
}

/* 在 pos 之后插入：先接新节点两头，再接邻居，最后改 pos->next——顺序不能乱 */
void list_insert_after(DNode *pos, DNode *n)
{
    if (pos == NULL || n == NULL || n->prev != NULL || n->next != NULL)
        return;                       /* 已挂链的节点不允许重复插入 */
    n->prev = pos;
    n->next = pos->next;
    pos->next->prev = n;              /* 用了尾哨兵，pos->next 一定非空 */
    pos->next = n;
}

/* 脱链：邻居互指，再把自己的指针清空（防御二次删除） */
void list_unlink(DNode *n)
{
    if (n == NULL || n->prev == NULL || n->next == NULL)
        return;                       /* 已脱链的节点直接返回 */
    n->prev->next = n->next;
    n->next->prev = n->prev;
    n->prev = n->next = NULL;
}

/* 把节点移到表头（LRU 的命中操作）：脱链 + 插到哨兵之后，均 O(1) */
void list_move_front(DList *l, DNode *n)
{
    list_unlink(n);
    list_insert_after(l->head, n);
}

DNode *list_find(DList *l, int key)
{
    if (l == NULL)
        return NULL;
    for (DNode *p = l->head->next; p != l->tail; p = p->next)
        if (p->key == key)
            return p;
    return NULL;
}
```

得分点：
1. `list_unlink` 只需改**前后两个节点**的指针，O(1)。单链表只能沿 `next` 找前驱，O(n)——所以"删节点"这个操作在单链表上要么 O(n)，要么用"**复制后继的值再删后继**"的技巧（只能用于非尾节点）。
2. **哨兵把"边界"变成了"普通情况"**：没哨兵时要为"删头节点/插到尾部"写 4 种分支，有哨兵时只有一套逻辑。代价是多两个哑节点（每个 12~24 字节），对嵌入式来说要权衡。
3. 插入后 `n` 已挂链，**再插一次会破坏链表**；`list_insert_after` 里"n 必须未挂链"的检查是防御性的，能提前暴露 bug。
4. 真实场景：**LRU 缓存**（`list_find` + `list_move_front` + 删尾 = 全是 O(1)，`list_move_front` 是点睛之笔）；**RTOS 的就绪表/事件链表**；Linux 内核的 `list_head` 双链表（它用"内嵌节点"技巧让同一结构体同时挂在多条链表上）。
   （真题同款：[2019 应用岗编程题"双向链表的创建、删除、插入、修改、查找"](/embedded-interview/hikvision-written-test.md)、[P5-Q02 链表实现队列](/embedded-interview/hikvision-written-test.md#p5q2)。注意：从 `list_unlink` 能看出为什么**链表实现队列 / LRU 都是"双向"**。）
复习：[C07 链表](/embedded-interview/c-basics.md#c07)、真题 [P1-Q23 链表的正确描述](/embedded-interview/hikvision-written-test.md#p1q23)

**C1-1 → B。**【实测：`sizeof(S1)=12, sizeof(S2)=8`】
S1：`a` 偏移 0；`b` 4 对齐 → 偏移 4（填 3）；`c` 偏移 8；`d` 2 对齐 → 偏移 10~11；整体按 4 对齐 → 12。
S2 用 `pack(1)` 取消对齐与填充：`1 + 4 + 1 + 2 = 8`。
**代价**：`pack(1)` 后成员可能不在自然边界上，某些架构（如 ARMv5 之前的 ARM、部分 MIPS）访问未对齐地址会**触发异常**，Cortex-M 默认允许但会拆成多次访问；工程上常配"访问时用 `memcpy` 拷到对齐变量"。

**C1-2 → A（①）。**
- ① ✔ `(*(volatile uint32_t *)0x40021000)` 把地址转成"指向 volatile uint32_t 的指针"再解引用，**每次访问都真实发生**，且常量地址在编译期就被放进指令/立即数，不占 RAM。
- ② ✘ 少了 `volatile`：编译器可以把多次读合并、把结果缓存在寄存器里——对"硬件会自己改变"的寄存器是致命的。
- ③ ✘ **能编译通过，但有隐患**：`REG3` 是一个**全局指针变量**，它自己（指针值）存在 RAM 里、可以被人改写，多数工程更倾向于用宏/常量；而且初学者常写成 `volatile uint32_t *REG3` 后误以为是"指向 volatile 的常量指针"——其实是"**指针可变、指向 volatile**"，要表示常量指针得写 `uint32_t * const volatile REG3`。
- ④ ✘ 把地址**值**转成 `uint32_t` 再解引用，类型错误（`uint32_t` 不是指针），无法通过编译。

配套考点：`volatile` 保证"访问不被优化"，但**不保证原子性、不是内存屏障、不处理缓存一致性**（例如 Cortex-A 上开了 D-Cache 后访问外设还得考虑 DMA 一致性问题）。

**C1-3 → B。** 通信帧结构体两端（不同编译器/不同 CPU）必须"字节布局一致"；不加 `pack(1)` 时编译器会插填充字节，双方 `sizeof` 和偏移都可能不同。

**C1-4 → C。** 轮询适合"事件率确定、实时性要求低、资源紧张"的场景；A/B/D 都需要低延迟响应，应该用中断。

**C1-5 → B。** `malloc` 在 ISR 里不可用（非可重入、可能阻塞）；而且频繁小块分配会产生碎片，在只有几十 KB RAM 的 MCU 上是长期隐患。改用**静态缓冲区 + 内存池**，或用 `xQueueSendFromISR` 直接把固定大小的结构体按值传过去。

**C2-1 → ABCD。** 四条都是 ISR 的大忌：
- A ✔ `printf`/串口写是阻塞的，会让中断延迟暴涨，还可能和主循环抢同一个 UART。
- B ✔ `malloc` 不可重入、可能阻塞，且长期产生碎片（见 [C1-5](#c1-5)）。
- C ✔ `xSemaphoreTake(..., portMAX_DELAY)` 在设计上就会阻塞，ISR 里必须用 `FromISR` 版本。
- D ✔ 即使没有阻塞，**长耗时处理也会让同优先级及更低优先级的中断被挂起**——这就是 [C4-1](#c4-1) 那 8 ms 打印问题的同类错误。

**C2-2 → ABD。** C 错：高优先级任务每次循环都喂狗，就等于"只看最高优先级任务活着"，低优先级任务死锁时看门狗照样被喂，设备卡住却不复位。正确策略：所有任务各报心跳，看门狗任务**检查全部心跳齐全**才喂狗。

复习：[R05 FromISR API](/embedded-interview/rtos.md#r05)、[R09 软件定时器回调](/embedded-interview/rtos.md#r09)

**C2-3 → ABC。** D 错：位数高只是理想分辨率高，参考电压噪声、PCB 地平面、采样时间不足一样会毁掉精度。**另见** [M09 ADC 位数越高越准吗](/embedded-interview/mcu-peripherals.md#m09)。

**C3-1 → ① `R | (1u << 3)`**（`R | 0x08` 等价）。
**关键点 1：置位用 `|`，清位用 `& ~`，翻转用 `^`** —— 三者都不能写成 `=`，否则会把其他位一起改掉。
**关键点 2（本题的真正坑）：这条语句对普通 RAM 变量是"安全"的，但对硬件寄存器只是"意图正确"**：

```c
R |= (1u << 3);        /* 展开为 R = R | (1u << 3); —— 读—改—写三步 */
```

在"读"和"写回"之间，如果硬件本身会改变该寄存器的其他位（典型例子：**写 1 清零的 `SR` 状态位、边沿触发后自动清除的中断标志**），读到的旧值再写回去就会**把硬件刚置上的位误清**。这就是"`R | mask` 看起来没问题、现场却偶发丢中断"的经典原因。
工程做法：
- 用 **bit-band 别名区**（Cortex-M3/M4 支持）对一个位做真原子读写；
- 或者对"不能读—改—写"的寄存器，**构造完整的目标值一次写入**（`R = (R & ~mask) | val` 也不够，要查手册确认哪些位是只写的）；
- 在 RTOS 多任务/中断共享的"软件寄存器"上，用 `portENTER_CRITICAL()` 包住读—改—写。

```c
/* 稳妥写法（不依赖位带） */
portENTER_CRITICAL();
R = R | (1u << 3);
portEXIT_CRITICAL();
```

**C3-2 → ② 50；③ 1500。**【实测：`72MHz / (72 × 20000) = 50Hz`】
`PSC + 1 = 72`，`ARR + 1 = 20000`；周期 `1/50 s = 20 ms`；每个计数 `1/(72MHz/72) = 1µs`；高电平 = 1500 µs（这是舵机的典型 1.5 ms 中位脉宽）。
复习：[M08 PWM 频率与占空比](/embedded-interview/mcu-peripherals.md#m08)

**C3-3 → ④ `0`；⑤ `0`；⑥ 一（第 1 个边沿，即上升沿）。** CPOL=0 表示空闲电平为低；CPHA=0 表示在**第一个边沿**（离开空闲电平的那个沿）采样，即上升沿。四个模式见 [M05 SPI 四种模式](/embedded-interview/mcu-peripherals.md#m05) 的表格。

**C3-4 → ⑦ `0x12345678`。**【实测】
小端：`buf[0]` 是**最低位字节**，所以 `0x78 | 0x56<<8 | 0x34<<16 | 0x12<<24 = 0x12345678`。

**C4-1 参考答案（12 分）**

逐条判：
- **① + `idx` 上界**：读 `DR` 取走字节本身是必须的，但 `idx` **没有上界检查**——收不到帧尾/协议不受控时 `buf[idx++]` 会写出数组 → **栈/静态区越界，HardFault**。这是比 ③ 更隐蔽的崩溃源。（另外若该 UART 有硬件 FIFO，应循环读空 FIFO，而不是每次中断只读 1 字节。）
- **② 有问题**：`idx >= 2` 只是"读够 2 个字节"，**不是帧边界**——协议必须按帧头/长度/校验定界（与 [B4-1](#b4-1) 同源）。
- **③ 问题最大**：`LOG_INFO("frame: %s", buf)` 是**同步阻塞打印**，单次最长 8 ms——ISR 里阻塞 8 ms 会让同优先级及更低优先级的中断被挂起，主循环几乎停摆。改为：ISR 只把数据推进缓冲区，日志交给任务。
- **④** `strlen(buf)` 在 ISR 里本身不致命，但它暴露了设计错误：代码把**二进制/协议帧当字符串**处理。一旦帧里出现 `0x00`，`strlen` 就会提前截断，`%s` 打印到 `'\0'` 为止 → **数据被截半、中文多字节被拆断 → 乱码**。改为按**长度**处理（`memcpy` + `%.*s`，或直接 `fwrite`）。
- **⑤ `malloc`**：中断里分配不可重入、会碎片化；且失败时返回 NULL，这里没检查就 `memcpy` → 空指针崩溃（HardFault）。改用静态池 / 固定队列元素。
- **⑥ 阻塞发送**：`xQueueSend(..., portMAX_DELAY)` 在 ISR 里**不能调用**，必须用 `xQueueSendFromISR(..., &woken)`，并在 ISR 末尾 `portYIELD_FROM_ISR(woken)`。
- **⑦ `memset` 清零 256 字节**：本身不算错（只是不便宜），真正的风险在于 `static buf`/`idx` 是**共享的可重入状态**——若这个 ISR 被更高优先级中断抢占并修改同一 `buf`，数据会被踩。
- **⑧ 清中断标志**：清法的**顺序**很关键，必须以芯片手册为准。很多 MCU 上"读 `DR` 即清 `RXNE`"，那就**不需要**再手写清标志；而在 Cortex-M 的 NVIC 层面**本来就不需要手动清中断**（外设标志清了就行）。写错会丢字节或中断触发不了。

"主循环卡顿一下"：最可疑的是 **③ 同步打印**（8 ms 阻塞）与 **⑤⑥ 分配 + 阻塞发送**（真实的时间开销 + 任务被挂起）。它们都在中断上下文里"花真实的时间"，而主循环的调度被中断延迟压制。
复习：[M03 UART 中断/DMA/IDLE 配合](/embedded-interview/mcu-peripherals.md#m03)、[R05](/embedded-interview/rtos.md#r05)

**C4-2 参考答案（14 分）**

1. （6 分）排查顺序（写到 5 步即可）：
   - **① 读复位原因寄存器**：区分是上电复位、看门狗复位、软件复位还是 BOR。若真是看门狗，说明是"软件死在某处"，不是电源问题。
   - **② 记录看门狗复位前的"现场快照"**：把当前任务名/栈/最后执行的日志行号/心跳时间戳存到**不丢电的 RAM 或 Flash 的保留扇区**，下次上电打印出来。
   - **③ 定量复现**：把超时时间调短/加日志，观察"复位周期是否受某个操作影响"（例如只在网络对端挂掉时复位、或只在温度高时复位）。
   - **④ 检查喂狗点**：看是"所有任务都活着才喂"还是"一个任务喂"；检查是否有中断里也喂了狗。
   - **⑤ 检查栈与堆**：任务栈溢出（FreeRTOS 可开 `configCHECK_FOR_STACK_OVERFLOW`）、堆碎片、`malloc` 失败返回 NULL 后继续用。
   - **⑥ 检查中断风暴**：某个中断未清标志导致无限重入，主循环永远拿不到 CPU → 喂狗任务得不到运行。
   - **⑦ 长时间阻塞的 API**：`xQueueReceive(..., portMAX_DELAY)` 在异常情况下永远等不到，喂狗任务反而被饿死。
2. （4 分）正确策略：
   - 每个任务**周期上报心跳**；由一个**独立看门狗任务**检查"是否所有任务的心跳都在有效期内"，齐全才喂狗。
   - "只有最高优先级任务喂狗"危险，因为它**只能证明自己活着**：低优先级任务死锁/饿死时，高优先级任务照样会喂狗，看门狗完全失效——设备名义上"活着"，实际已经无法工作。
   - 另外：**中断里不喂狗**、喂狗点不要与业务逻辑混在同一个循环里（防止"在死循环里被喂狗"）。
3. （4 分）最小化快照方案：
   - 保存：复位原因寄存器值、复位前的 `pc`/`lr`（若硬件支持）、每个任务名 + `uxTaskGetStackHighWaterMark`、最近 N 条日志环形缓冲区（时间戳 + 模块 + 事件码）、当前网络状态等关键变量。
   - 存储：专用 RAM 区（`.noinit` 段，复位不清零）或 Flash 保留扇区（每次更新一条，写入前先擦）。
   - 读出：上电时判断"是否是从看门狗复位来的"，如果是就打印该快照。
   - 关键：**每次写快照前后要保证一致性**（用"产生序号 + 校验"双写防写坏；先写数据再写"有效标志"）。

**C5-1 参考答案（14 分）**

```c
static uint8_t crc8_bit(const uint8_t *data, size_t len)
{
    uint8_t crc = 0x00;
    for (size_t i = 0; i < len; i++) {
        crc ^= data[i];
        for (int b = 0; b < 8; b++)
            crc = (crc & 0x80) ? (uint8_t)((crc << 1) ^ 0x07)
                               : (uint8_t)(crc << 1);
    }
    return crc;
}
```

```c
static uint8_t crc_table[256];

static void crc8_table_init(void)
{
    for (int i = 0; i < 256; i++) {
        uint8_t crc = (uint8_t)i;
        for (int b = 0; b < 8; b++)
            crc = (crc & 0x80) ? (uint8_t)((crc << 1) ^ 0x07) : (uint8_t)(crc << 1);
        crc_table[i] = crc;
    }
}

static uint8_t crc8_tab(const uint8_t *data, size_t len)
{
    uint8_t crc = 0x00;
    for (size_t i = 0; i < len; i++)
        crc = crc_table[crc ^ data[i]];
    return crc;
}
```

【实测】`crc8_bit` 与 `crc8_tab` 对 `01 02 03 04` 都输出 **`0xE3`**。

为什么用查表：逐位法每字节要做 8 次"移位 + 异或 + 判断"，约 **8~24 个 CPU 周期/字节**；查表法每字节只需 **1 次异或 + 1 次查表**，通常 **几个周期/字节**，速度提升约一个数量级，代价是 **256 字节**的表（Flash 或 RAM）。串口高波特率下，逐位 CRC 可能吃满 CPU，查表法很常见。
（工程注意：表可以放 Flash 用 `const`，省 RAM；也可以"运行时只算一次"）

第 3 问：发送 `01 02 03 04` 得到 **`0xE3`**（初值 0、多项式 0x07、不反射）。**不同初值/反射/异或输出会得到不同结果**，所以作答时把参数写清楚——这正是现场"两边 CRC 对不上"最常见的原因。

**C5-2 参考答案（16 分）**

```c
static size_t rb_used(const rb_t *r) { return r->head - r->tail; }
static size_t rb_free(const rb_t *r) { return RB_SIZE - rb_used(r); }

int rb_put(rb_t *r, uint8_t v)
{
    if (rb_free(r) == 0)
        return -1;                       /* 满：拒绝，绝不覆盖 */
    r->buf[r->head % RB_SIZE] = v;
    r->head++;                           /* 计数器只增不减 */
    return 0;
}

int rb_get(rb_t *r, uint8_t *v)
{
    if (rb_used(r) == 0)
        return -1;                       /* 空 */
    *v = r->buf[r->tail % RB_SIZE];
    r->tail++;
    return 0;
}
```

【实测】写满 8 个后第 9 次 `rb_put` 返回 `-1`（满），`used = 8`；取走 2 个后 `used = 6`，下一次 `put` 成功。

得分点：
1. **"满与空"都表现为 `head == tail`** 的经典陷阱，用"计数器差值"或"留一个空位"来区分——本题用差值法，最简单。
2. **`head`/`tail` 只增不减**、索引用 `% RB_SIZE`：这样 `used = head - tail` 永远正确，不需要为"环绕"写特殊分支。
3. **PUT 端只改 `head`、GET 端只改 `tail`**——这正是单生产者/单消费者能无锁的前提（见 [A4-1 第 3 问](#a4-1)）；但**索引的"读 + 写回"本身仍不是原子操作**，而 `head`/`tail` 的更新是否安全取决于宽度：在 32 位 MCU 上对齐的 32 位 `size_t` 单次读写是原子的，但 `head - tail` 这种"读两个变量再比较"仍可能读到**一前一后不一致的快照**；在 8 位/16 位 MCU 上连单个 `size_t` 的读写都不是原子的。所以：**用 `rb_used()` 判断之前，最好保证 `head` 的读取顺序合理，或干脆加临界区。**

第 2 问：如果 `head`/`tail` 是 `size_t`（32 位）且**无符号**，会**静默回绕**（越过 `2^32` 后回到 0）——只要"差值"不超过 `RB_SIZE`，`head - tail` 依旧是正确的；这是无符号环绕的巧妙之处。但这也意味着**一旦某个生产者/消费者写错，差值超出 `RB_SIZE`，满/空判断会全部失效**，而且很难复现（要跑很久才会回绕）。所以工程上二选一：
- **限制总写入量**，或用 64 位计数器（几乎不可能触发）；
- 或**利用回绕归零**：当 `used == 0` 时执行 `head = tail = 0`——这一句必须在"计数器回绕之前"的一个安全窗口里完成，否则反而破坏一致性，所以通常只在"缓冲区确认为空"时做，且加临界区。

第 3 问：

```c
/* 小端：buf[0] 是最低字节 */
uint32_t le = (uint32_t)buf[0] | ((uint32_t)buf[1] << 8) |
              ((uint32_t)buf[2] << 16) | ((uint32_t)buf[3] << 24);

/* 大端：buf[0] 是最高字节 */
uint32_t be = ((uint32_t)buf[0] << 24) | ((uint32_t)buf[1] << 16) |
              ((uint32_t)buf[2] << 8) | (uint32_t)buf[3];
```

【实测】`01 02 03 04` → 小端 = `0x04030201`，大端 = `0x01020304`。
**要点：必须用 `(uint32_t)` 显式提升**——`buf[0] << 24` 中 `buf[0]` 会被提升为 `int`，如果最高位是 1（例如 `0x80`），`0x80 << 24` 在有符号 `int` 上是**未定义行为**（溢出）；先转成 `uint32_t` 再移位完全合法。
