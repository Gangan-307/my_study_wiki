# 工程调试与项目追问

[返回专区](index.md) | [复习与自测表](review-plan.md)

学习要求：用“现象、假设、证据、原因、修复、验证”讲述问题。排查模板用于指导实验，不能把猜测写成已确认根因，也不能把预期结果写成测量数据。

## D01：编译报错与链接报错怎么区分？

**参考回答：** 常见构建流程包括预处理、编译、汇编、链接。语法、类型或头文件错误通常发生在前面阶段；`undefined reference` 常表示链接时找不到所需定义，`multiple definition` 常表示重复定义。先找到第一个有意义的错误，再查完整构建命令。

**易错点：** 有头文件声明不等于有函数实现参与链接；库顺序、宏开关、源文件是否加入工程、C/C++ 名字修饰和 ABI 都可能影响链接。不要只看 IDE 最后一行“构建失败”。

**面试追问：** 同事可以编译，你不行，除了源码还需要比对哪些条件？如何查看预处理结果、符号表与链接 map？

## D02：遇到 HardFault、Panic 或段错误怎么查？

**参考回答：** 先保留固件版本、完整日志、复现步骤和异常现场，再结合匹配的 ELF 与调试信息定位。Cortex-M 可以检查有效的异常堆栈、PC/LR/SP 及芯片支持的故障状态寄存器；ESP-IDF 使用 Panic/回溯与对应工具；Linux 使用 core dump、GDB 等。

**易错点：** 崩在某个库函数不证明库就是根因，可能之前已经破坏内存。不是所有 Cortex-M 都有相同故障寄存器，异常栈也可能已损坏。地址解析必须使用与运行二进制匹配的 ELF，不能随手拿最新编译版本。

**面试追问：** `memcpy` 崩溃时，怎样核对源地址、目标地址、长度、生命周期和并发修改？

## D03：内存泄漏、碎片和资源不足有什么区别？

**参考回答：** 泄漏是本应释放的资源持续失去回收机会；碎片是空闲区域分散，可能总量足够却没有合适连续块；资源不足还可能来自真实峰值需求或特定内存区域限制。应同时记录空闲量、最小剩余、最大可分配块、分配失败位置和重复操作后的趋势。

**易错点：** Linux 的文件缓存增长不直接等于应用泄漏；只看整机 `free` 不能定位进程堆问题。ESP32 的内部 RAM、PSRAM、DMA 能力约束不同，空闲总和不能保证某个 capability 的分配成功。

**面试追问：** 每次 BLE 重连后少一块内存，如何检查连接对象、定时器、回调上下文和错误退出路径？

## D04：栈溢出、越界和悬空指针怎么区别？

**参考回答：** 栈溢出是运行栈超出分配范围；越界是访问超过某个对象边界；悬空指针指向生命周期已结束的对象。三者都可能破坏别的数据。结合栈水位、保护机制、堆检查、调试器观察点和主机侧 Sanitizer 分别查证。

**易错点：** MCU 没有触发异常不代表没有越界，错误地址可能仍落在可访问 RAM。增大栈或插入变量后现象消失，只能作为线索。GDB watchpoint 能否生效受硬件数量、访问宽度和目标调试能力限制。

**面试追问：** 为什么释放后的指针偶尔还能读出原值？你如何证明一处修复解决了生命周期问题？

## D05：加 `printf` 后故障消失，说明什么？

**参考回答：** 日志改变执行时序、栈使用、内存布局和同步行为，可能掩盖竞态、栈问题或未定义行为。应保留线索，比较优化级别和复现条件，用更低干扰的计数、时间戳、GPIO 测时或跟踪工具继续验证。

**易错点：** “延时后就好”不是根因分析。关闭优化、加 `volatile`、增大所有缓冲区都不能作为通用结论。修复后仍应恢复原来的负载和优化配置进行验证。

**面试追问：** 如何证明是生产者提前复用了缓冲区，而不是“CPU 太快”？可以在哪个交接点记录所有权变化？

## D06：看门狗复位，是不是喂狗频率不够？

**参考回答：** 看门狗用于检测系统或任务未在规定时间内正常推进。要先识别是哪类看门狗、哪个执行上下文被监控，检查忙循环、长时间关中断、死锁、任务饥饿和阻塞 I/O。复位原因与监控对象共同决定排查方向。

**易错点：** 无条件提高喂狗频率或关闭看门狗可能掩盖故障。由一个始终能运行的高优先级任务喂狗，也可能无法检测业务任务已死锁。健康检查应反映关键任务实际完成进度，而不只看“线程还活着”。

**面试追问：** OTA 或 Flash 擦写耗时较长时，如何合理设计超时、任务调度和监控，而不是简单取消保护？

## D07：日志、示波器、逻辑分析仪、GDB、strace 怎么选？

**参考回答：** 先判断问题在哪一层，再选择能给直接证据的工具。

| 工具 | 适合观察 | 不能直接证明什么 |
| :--- | :--- | :--- |
| 日志/计数 | 程序状态、错误码、丢包趋势 | 没有日志不一定代表代码没执行 |
| 示波器 | 电压、边沿、噪声、波形时序 | 协议业务处理是否正确 |
| 逻辑分析仪 | 数字边沿与 UART/I2C/SPI 解码 | 模拟电气质量一定合格 |
| GDB/调试探针 | 调用栈、寄存器、变量、断点 | 暂停调试不会改变实时行为 |
| strace | Linux 系统调用与返回值 | 所有用户态函数调用与 MCU 内部执行 |

**易错点：** 逻辑分析仪解码前要确认电平阈值、采样率、位序和协议模式。`strace` 会引入开销；优化构建中的源码单步顺序和变量位置可能与直觉不同。

**面试追问：** UART 丢字节时，怎样比较线上是否已发送、外设是否溢出、软件队列是否已满？

## D08：如何证明项目稳定，而不只说“运行正常”？

**参考回答：** 先定义可观察的成功标准，再覆盖正常、边界和异常场景。记录版本、负载、次数、运行时长、资源趋势、错误计数与恢复结果。性能优化需要同条件下的基线和修改后数据，成功率需要明确样本和成功判定。

**易错点：** 一次成功不能推出长期稳定，24 小时运行也只覆盖当时的条件。测试 20 次成功 17 次可以报告这组样本为 85%，但不能直接声称所有场景成功率 85%。未做过的断电、丢包或功耗测试不能写入简历成果。

**面试追问：** 机械臂分拣的“成功”如何定义？手表 OTA 的正常下载、错误镜像、断网恢复分别怎样验收？

## D09：为什么工程能力还包括 Git 和可复现构建？

**参考回答：** 代码、SDK、编译器、配置、依赖和必要的生成步骤共同决定构建结果。Git 用于追踪改动、定位引入问题的提交、审查与协作；README 应说明从干净环境构建、烧录和运行的方法。

**易错点：** 本机能编译可能依赖未提交文件或绝对路径。`git diff` 默认查看未暂存的已跟踪改动，暂存区用 `git diff --cached`，新文件用 `git status` 检查。不要用覆盖未保存工作的方法处理构建问题，也不要把客户代码和凭据混入公开项目。

**面试追问：** 昨天版本正常、今天失败，如何在独立工作目录里复现和二分定位？一次修复提交应留下哪些验证信息？

## D10：项目介绍怎么讲？AI 辅助的代码怎样准备追问？

**参考回答：** 先说明需求与约束，再讲数据流、自己负责的模块、一个具体技术选择和一次有证据的故障修复。区分 SDK 已有能力、自己集成的部分和独立实现的部分。AI 辅助内容需要能解释资源所有权、并发、边界和失败路径。

**易错点：** 罗列十个功能不如把一个关键流程讲清楚。不要把框架默认支持说成自己实现，也不要把没有参与的部分写成独立开发。遇到不懂的细节，说明已知范围和验证方法，不能编造原理。

**面试追问：** 删除这条错误检查会怎样？数据长度翻倍后哪里会先出问题？从 UART 改成 BLE 后，哪些模块可以复用、哪些要调整？

**两分钟模板：**

```text
需求：这个设备要完成什么，资源和实时性约束是什么。
职责：我实际负责哪些模块，使用了哪些已有框架。
流程：数据从哪里产生，经过哪些任务/模块，最终去哪里。
难点：一次真实失败，如何复现，用什么证据确认原因。
结果：改了什么，如何回归，当前仍有哪些限制。
```

## 动手验证

下面的完整程序可在 WSL 或泰山派运行，用于区分普通函数、系统调用与进程行为。保存为 `hello_process.c`。

```c
#include <stdio.h>
#include <unistd.h>

int main(void)
{
    if (printf("pid=%ld, ppid=%ld\n", (long)getpid(), (long)getppid()) < 0) {
        return 1;
    }
    if (fflush(stdout) == EOF) {
        return 1;
    }
    return 0;
}
```

```bash
gcc -std=c11 -Wall -Wextra -O0 -g hello_process.c -o hello_process
./hello_process
strace -o hello_process.strace ./hello_process
tail -n 15 hello_process.strace
gdb ./hello_process
```

进入 GDB 后依次使用 `break main`、`run`、`next`、`bt`、`continue`、`quit`，解释断点、单步和回溯各解决什么问题。`strace` 的内容依 libc 和系统版本而异，里面不会列出每个普通 C 函数。

- [ ] 找到输出对应的 `write`，解释 `printf` 与系统调用的关系。
- [ ] 选择一个自己的 ESP32 实习问题，整理脱敏复现、证据、修改与回归结果。
- [ ] 为主项目画一张模块/数据流图，准备 D10 的两分钟口述。
- [ ] 为一个修复补充正常、边界和异常测试，不填写未测得的性能或成功率。
