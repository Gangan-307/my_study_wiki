# RTOS 与并发易错题

[返回专区](index.md) | [复习与自测表](review-plan.md)

学习要求：能画出任务状态与数据流，说明数据由谁拥有、谁等待谁、超时后如何恢复。以下以常见抢占式 FreeRTOS 为主，涉及 ESP-IDF、RT-Thread 和多核时单独说明。

## R01：任务有哪些状态？优先级越高就一直运行吗？

**参考回答：** 常见任务状态有运行、就绪、阻塞和挂起。在单核抢占式配置下，调度器通常选择最高优先级的就绪任务运行。任务等待队列、信号量或延时后进入阻塞，CPU 可以运行其他就绪任务。同优先级任务是否时间片轮转取决于配置。

**易错点：** FreeRTOS 通常是数字越大任务优先级越高，RT-Thread 通常相反。高优先级任务一直忙轮询，可能饿死低优先级任务。主动 yield 通常不能让仍就绪的高优先级任务把 CPU 持续让给低优先级任务，应使用合适的阻塞等待。

**面试追问：** 两个任务同时打印，日志交替出现能证明优先级相同吗？调用 `printf`、锁等待和阻塞会如何影响现象？

## R02：`vTaskDelay` 和 `vTaskDelayUntil` 有什么区别？

**参考回答：** `vTaskDelay` 相对调用时刻的 Tick 计数延时，循环执行时间会叠加到周期中；`vTaskDelayUntil` 根据上次唤醒基准维持周期，更适合周期采样。应使用 `pdMS_TO_TICKS` 等接口表达毫秒与 Tick 的转换，并检查结果与精度。

**易错点：** Tick 是调度时间基准，不等于精确的微秒延时。延时结束只表示任务可就绪，不保证马上得到 CPU。过短的毫秒值可能转换成 0 Tick，任务执行时间超过周期时也不能靠延时 API 补回实时性。

**面试追问：** 每轮采集用 7ms，再 `vTaskDelay(pdMS_TO_TICKS(10))`，周期为什么可能大于 10ms？高精度 PWM 为什么交给硬件定时器？

## R03：队列、信号量、互斥锁和事件组怎么选？

**参考回答：** 先区分目的是传数据、记录事件、保护资源，还是等待多个状态，再选择同步原语。

| 原语 | 主要用途 | 容易遗漏的条件 |
| :--- | :--- | :--- |
| 队列 | 传递固定大小的数据项 | 容量、满队列策略、按值复制还是传指针 |
| 二值信号量 | 表示一次待处理通知 | 不累计多次事件，也没有互斥锁的所有者语义 |
| 计数信号量 | 统计资源数量或事件数 | 最大计数、溢出与消费者速度 |
| 互斥锁 | 保护任务间共享资源 | 持有者释放、优先级继承、禁止在 ISR 中使用 |
| 事件组 | 按位等待 AND/OR 条件 | 重复置位不计次数，清位与唤醒语义 |
| 任务通知 | 向指定任务传状态或计数 | 通知动作、索引和覆盖规则需明确 |

**易错点：** 二值信号量与互斥锁即使 API 相似，也不能不加分析地互换。多个任务可以等待同一个信号量，但一次成功获取只能归其中一个等待者，不是广播。

**面试追问：** UART ISR 通知解析任务选什么？多个任务访问 I2C 总线选什么？每个采样值都不能丢时又选什么？

## R04：什么是优先级反转？优先级继承能解决一切吗？

**参考回答：** 低优先级任务 L 持锁，高优先级任务 H 等锁而阻塞；中优先级任务 M 抢占 L，导致 H 被间接拖延。互斥锁的优先级继承可以暂时提高持锁任务优先级，让它尽快释放资源。

**易错点：** 优先级继承不能解决死锁，也不能让锁内的慢速 I/O 变快。FreeRTOS 的继承实现有简化，持多个锁时的降级细节要看版本。临界区仍应短，尽量不在持锁期间做长时间阻塞操作。

**面试追问：** 如果 L 一直不释放锁，继承是否有用？为什么保护 I2C 事务时要考虑超时和错误退出释放锁？

## R05：为什么 ISR 要用 `FromISR` API？

**参考回答：** ISR 不能像任务一样阻塞等待，FreeRTOS 提供特定的中断上下文 API 进行通知或数据转交。需要检查 API 返回值，在唤醒了更高优先级任务时按移植层要求请求中断退出后的调度。

**易错点：** `FromISR` 不是所有硬件中断都能调用的通行证，还要满足该端口的中断优先级限制。互斥锁不能用于 ISR；普通 `malloc`、复杂日志和阻塞传输也不应未经分析就放入 ISR。

**代码片段：** 下例需放入已初始化队列的实际 ISR 中，前提是中断优先级允许调用内核 API；`byte` 来自接收寄存器，硬件标志清除按芯片手册处理。

```c
BaseType_t woken = pdFALSE;
BaseType_t result = xQueueSendFromISR(rx_queue, &byte, &woken);
if (result != pdPASS) {
    /* Count dropped bytes; do not block in the ISR. */
    rx_drop_count++;
}
portYIELD_FROM_ISR(woken);
```

`rx_drop_count` 在该 ISR 外读取或修改时也需要分析并发访问，不能靠这个计数片段代替同步设计。

**面试追问：** 如果队列满了，返回成功还是失败？记录丢包、丢弃新数据和覆盖旧数据分别适合什么场景？

## R06：队列传指针会复制数据吗？事件组会保存每次事件吗？

**参考回答：** FreeRTOS 队列按创建时的数据项大小复制内容。队列项是指针时，只复制指针值，不复制它指向的整块数据。事件组保存位状态，同一个位连续置位不累计次数；符合等待条件的多个任务可以被唤醒。

**易错点：** 把局部数组地址排队后离开作用域，或生产者提前复用缓冲区，会导致消费者读到无效或被覆盖的数据。需要传值、内存池、引用计数或明确的归还机制。`xEventGroupSetBitsFromISR` 通过定时器服务任务延后处理，命令队列满时可能失败。

**面试追问：** 每 1ms 采样一次，但消费者每 10ms 才处理，单个事件位为什么不能保证样本完整？

## R07：死锁、饥饿和竞态有什么区别？

**参考回答：** 死锁是任务形成无法推进的资源等待关系；饥饿是任务长期得不到运行或资源机会；竞态是结果依赖未正确约束的执行顺序。死锁常涉及互斥、占有且等待、不可抢占和循环等待等条件。

**易错点：** 给获取锁增加超时能提供退出机会，但不是自动修复，必须释放已持有资源并定义重试策略。常用措施是统一加锁顺序、减少嵌套、明确所有权。简单关中断不能解决跨核共享问题。

**面试追问：** A 先拿锁 1 再拿锁 2，B 反过来，怎样用固定顺序修复？超时后两者同时重试会不会持续互相干扰？

## R08：任务栈多大合适？FreeRTOS 栈大小单位是什么？

**参考回答：** 原生 FreeRTOS 的 `xTaskCreate` 栈深度通常按 `StackType_t` 元素个数传入；ESP-IDF 的任务创建 API 使用字节单位，必须对照具体版本文档。栈预算考虑局部数组、函数嵌套、格式化输出、库调用和最坏路径，再用水位与溢出检查验证。

**易错点：** 高水位通常表示历史最小剩余量，不是最大已使用量，单位也要按端口核对。某个入口函数很短，不代表调用的 TLS、音频或格式化函数耗栈很少。测试路径未覆盖时，较大剩余量不能证明所有情况安全。

**面试追问：** 增大任务栈后崩溃消失，为什么仍不能立刻确认根因？越界写是否可能只是换了破坏位置？

## R09：软件定时器回调在哪执行？能做耗时工作吗？

**参考回答：** FreeRTOS 软件定时器回调运行在定时器服务任务中，不是直接运行于硬件定时器 ISR。回调宜短，复杂工作交给其他任务。启动、停止等命令通常经命令队列提交，API 超时参数与回调本身执行时限不是一回事。

**易错点：** 多个回调共用服务任务，一个回调长时间阻塞会延迟其他回调和相关延后处理。软件定时器也不能保证精确硬实时。ESP-IDF 的其他定时接口可能支持不同派发方式，不能都按 FreeRTOS 软件定时器理解。

**面试追问：** 在定时器回调里进行同步 HTTP 下载会影响什么？改成通知下载任务后如何避免重复启动同一工作？

## R10：关中断、挂起调度器、加锁有什么区别？多核呢？

**参考回答：** 关中断影响中断响应范围，挂起调度器影响任务切换，加锁协调遵守同一锁协议的执行上下文。单核短临界区可通过屏蔽特定中断实现，但多核还要考虑另一个核心；ESP-IDF 的相关临界区接口结合自旋锁处理跨核互斥。

**易错点：** 屏蔽中断的具体范围取决于架构和移植；挂起调度器不等于关中断，也不是跨核保护。不要在持自旋锁的临界区里睡眠或做长 I/O。绑定任务到某个核心不会自动解决它与其他核心或 ISR 的共享数据问题。

**面试追问：** 一个核心修改链表，另一个核心读取，为什么仅在写入核心关中断不够？怎样缩短锁覆盖的范围？
