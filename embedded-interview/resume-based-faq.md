## 怎么用

1. **每题先看"简历锚点"那一行。** 它决定这道题该讲多深：锚点标 `防御` 的，只讲原理、别往项目上引；标了具体编号（如 `S3`、`W2`）的，可以带一句真实经历。
2. **每题都按同一结构走**：`简历锚点` → `参考回答`（可以直接说的几句）→ `追问链`（面试官往下追两层的方向）→ `易错`（当场会减分的答法）。先自己答一遍再看后两栏。
3. **保守口径**：凡是 `防御` 题，参考 [答案稿_04 第五节](/daily/求职准备/答案稿_04_技能栏与基础题.md) 的撤退三句——"知道现象不知道原理 / 数值记不准 / 没做过但做过相邻的事"。
4. **标 ⚠ 的是项目里最容易说错的点**，不是难点，是**边界**——说错一句比答不出更贵。

> 答题总则：**先结论、再条件、最后一句项目落点**。没有项目落点就停在前两步，不要硬编。

## 一、C 语言深水区（S1）

### E01：`__attribute__((packed))`、`aligned`、`weak`、`section`、`used` 分别在什么时候用？

**简历锚点**：S1（C 熟悉）＋ S2（三个平台）＋ [D1/D3](/daily/求职准备/简历3.0_全文还原与编号.md) 的协议与持久化——EEPROM 里存的参数结构体、BLE 帧结构，都是"`sizeof` 必须等于协议长度"的场合。

**参考回答**：GCC/Clang 的属性用来直接干预代码生成，常见五个：

| 属性 | 作用 | 典型用在哪 |
| :--- | :--- | :--- |
| `packed` | 去掉结构体成员间的填充 | 与外设/EEPROM/通信协议一一对应的结构体 |
| `aligned(n)` | 指定最小对齐 | 要求 4 字节对齐的 DMA 缓冲、栈上变量 |
| `weak` | 弱符号，有同名强符号时被覆盖 | ISR 默认空实现、SDK 预留的钩子函数 |
| `section(".xxx")` | 把变量放进指定段 | 升级标志位、版本号放到固定段便于读取 |
| `used` | 阻止被优化掉（"看起来没被引用"） | 中断向量表、只靠链接脚本引用的表项 |

**关键边界**：
- `packed` 只是**布局**变紧，**访问速度变慢**：ARM 上访问打包结构里的 32 位字段可能被编译器拆成多次字节访问，甚至在某些地址上需要对齐修正。所以包装/解包在**协议边界**做，内部运算用正常对齐的成员。
- `packed` 和 `aligned` 同时写要小心（`packed, aligned(4)` 表示可以去掉内部填充但整体 4 对齐）。
- 更严格、更"标准 C"的写法是 `_Static_assert(sizeof(frame_t) == PROTO_LEN, "...")`，把布局约束变成**编译期报错**。

**追问链**
- **"加了 `packed` 还能直接 memcpy 到网络缓冲吗？"** → 不能直接依赖，因为还要处理**字节序**（见 [E16](#e16)）；正确顺序是：收到缓冲 → 逐字段按协议解码 → 填进内部结构体。
- **"`weak` 函数被覆盖了怎么确认？"** → 看 MAP 文件里这个符号最终落在哪个目标文件的段里。

**易错**：说"`packed` 让程序更快/更安全"——都反了，它是用性能换布局确定；也不要上来就说"我们用 `#pragma pack(1)`"，那是 MSVC/Keil 的写法，交叉工具链是 GNU 属性。

### E02：`restrict`、`inline`、`_Static_assert`、`__PRETTY_FUNCTION__` 这些 C99/后续关键字怎么理解？

**简历锚点**：S1（C）/ S3（gcc + Keil AC5/AC6 两套编译器）。这题考的是"你会不会区分**语言标准**和**编译器扩展**"。

**参考回答**：
- `restrict`：告诉编译器"这段指针访问的对象在这期间只有它一个通路"，编译器可以乱序/缓存读写。典型用在 `memcpy(dst, src, n)` 的形参、DSP 循环。**违反了就是未定义行为**，比 `volatile` 更需要你敢担保。
- `inline`：C 里是给编译器的**建议**，不保证内联；`static inline` 放在头文件里是最常见的模块内联写法；纯 `inline` 在 C 里还有"外部定义在哪"的链接语义坑，头文件里更推荐 `static inline`。
- `_Static_assert`（C11）：编译期断言，常用来卡结构体大小、字段偏移、枚举取值，等价于 [E01](#e01) 说的"把布局约束变成编译错误"。
- `__PRETTY_FUNCTION__` / `__func__`：日志里打函数名，`__func__` 是标准 C99，`__PRETTY_FUNCTION__` 是 GCC 扩展（对 C++ 更好用）。

**追问链**："为什么宏做断言比 `_Static_assert` 差？" → 宏只能失败时抛出奇怪的错误信息，而 `_Static_assert` 直接带字符串说明。

**易错**：把 `inline` 说成"一定不会压栈"；把 `restrict` 和 `const` 搞混（前者是**别名约束**，后者是**可写性约束**）。

### E03 ⚠：C 里怎么实现位域替代、函数指针表、状态机、单例式模块接口？

**简历锚点**：S1（指针/位运算）＋ W3（按 `app / services / bluetooth / drivers / ui / resource` 分模块）＋ 药箱的分拣流程与手表的多页面切换，都很容易被要求"现场写个状态机"。

**参考回答**：面试官一般只想知道**三种结构的写法**，能写出来就行：

1. **函数指针表做命令/回调分派**：用 `const` 数组 + 枚举索引，比 `switch` 更好维护、也常被用来做驱动层的统一 ops 接口（`struct ops { int (*init)(void); ... };`）。注意**不要放出工厂模式那套 C++ 概念**，C 里就是表 + `NULL` 检查。
2. **表驱动状态机**：`{当前状态, 事件, 动作函数, 下一状态}` 四元组数组，处理函数只看表。好处是新增状态只加一行，出问题的状态可追踪。**要说明你项目里的具体状态机**——手表是页面状态（加载/回滚/卸载），药箱是分拣流程（待机→取药→移动→校验→回位）。
3. **模块单例接口**：头文件只暴露 `xxx_init / xxx_get_state / xxx_set_mode`，内部状态用 `static`，这样**换实现不动调用方**。这就是 C 里的"封装"。

**追问链**："状态机里动作失败了怎么处理？" → 动作函数返回错误码，表驱动框架统一走"错误状态/回退"，而不是每个 case 各写一套。

**易错**：把"状态机"讲成"用了 `if-else` 就是状态机"；也不要宣称"用到了分层架构/设计模式"却指不出符合那句话的 2 行代码。

### E04：Flash 上的常量、`const` 和 `static` 到底怎么分布？启动时谁把它们搬到 RAM？

**简历锚点**：S2（STM32 / ESP32 / SF32 三平台）＋ S3（Keil 与 gcc 两套构建）＋ [W1](/daily/求职准备/简历3.0_全文还原与编号.md) 的堆与栈统计，必然被问到"你日志里那块内存从哪来"。

**参考回答**：链接后几个关键段：

| 段 | 里面是什么 | 运行位置 |
| :--- | :--- | :--- |
| `.text` | 代码 + 字符串字面量 + `const` 数组（多数 MCU 工具链把 `const` 放 Flash） | Flash，直接执行 |
| `.rodata`（有的工具链并入 `.text`） | 只读常量 | Flash |
| `.data` | 已初始化的全局/静态变量，初值**存在 Flash 一份** | 启动时由启动文件拷进 RAM |
| `.bss` | 未初始化/初值为 0 的全局/静态变量 | 启动时清零 |
| `.heap` / `.stack` | 堆与栈 | RAM |

顺序是：复位 → `Reset_Handler` → 设栈指针 → 从 Flash 把 `.data` 初值拷到 RAM → 清零 `.bss` → 调 `SystemInit` → 跳到 `main`（完整启动过程见 [M10](mcu-peripherals.md#m10)）。

**追问链**
- **"`const` 变量一定在 Flash 吗？"** → 不一定：带 `volatile const` 的只读寄存器、以及某些工具链的配置会把它放 RAM；判断依据是 **MAP 文件里符号落在哪个段**，不是靠猜。
- **"`.data` 为什么在 Flash 里占两份？"** → Flash 里那份是初值镜像，RAM 里那份才是可写副本，所以镜像大小要算上它。
- **"SWD/调试器怎么知道堆到哪结束？"** → 链接脚本给 `_end`/`__bss_end` 之类的符号，RT-Thread 的 `rt_system_heap_init(HEAP_BEGIN, HEAP_END)` 就从 `__bss_end` 起算——这正是 [Q039](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md) 里"MAP 的 `.heap` 只有 3072 B、日志却报 247 488 B"的原因。

**易错**：说"`const` 一定在 Flash"，或把 `.heap` 段大小当成 RTOS 堆容量（Q039 里已经踩过）。

### E05：ARM Cortex-M 的中断、异常、`PendSV`、尾链、咬尾中断在 RTOS 里怎么用？

**简历锚点**：S2（FreeRTOS + RT-Thread）＋ [R05](rtos.md#r05)、[Q065](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md)（ISR 里能调什么）。八股常停在"`FromISR`、别阻塞"，追问一层就是 Cortex-M 的机制。

**参考回答**：
- 异常编号：1–15 是系统异常（`NMI`、`HardFault`、`SVC`、`PendSV`、`SysTick`），16 起是外部中断。**RTOS 的任务切换就是靠 `PendSV`**：SysTick 里只置 `PendSV` 挂起，等所有中断退出后再统一做上下文切换（"延迟切换"），这样不会打断中断处理。
- **咬尾（tail-chaining）**：一个中断退出时如果已经有更高优先级异常在挂起，硬件不还原现场直接进下一个异常，省掉 `return` 的开销。**尾链被中断抢占**则相反（late arrival）。
- **BASEPRI / PRIMASK**：关中断通常就是"写 BASEPRI 屏蔽到某个优先级"，比 `PRIMASK` 全局关更精细——RTOS 的临界区就是这么做，保留最紧急中断仍能响应。
- **NVIC 优先级分组**：Cortex-M 用抢占优先级 + 子优先级的位分配，数值小=优先级高；**它和 RTOS 任务优先级是两套体系**（[M06](mcu-peripherals.md#m06)）。FreeRTOS 还要求 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 以上的中断才能调 `FromISR` API。

**追问链**："中断优先级设错了会出现什么现象？" → 高频率中断把低优先级"饿死"、或者本该立即响应的中断被拖延，表现是**偶发的通信超时/乱序**——这时候用 GPIO 翻转+示波器测"进中断到执行完"的耗时最直接。

**易错**：说"RTOS 在 SysTick 里直接切任务"——直接切会在中断嵌套里破坏上下文，正规实现是 SysTick 触发 `PendSV`。

### E06：中断上下文里做一次 `snprintf`、`malloc`、`float` 运算，各有什么风险？

**简历锚点**：S1（C 熟悉）＋ 药箱 D1/D2 与手表 W2 的多任务协同——ISR 里该做什么，是"任务划分"那道题的对面。若被追问"你在 ISR 里调过什么 RTOS API"，只讲 [R05](rtos.md#r05) 和 [Q065](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md) 已备好的手表口径。

**参考回答**：按风险从高到低：
1. **`printf` / `snprintf`**：不可重入（共享内部缓冲）、耗时长、可能阻塞在 UART 发送，还可能占大量栈。只能改成**置标志 + 主循环里打印**，或者用环形缓冲把事后再打。
2. **`malloc/free`**：大多不是可重入的（堆管理结构会被打断），而且可能阻塞。MCU 上本来就优先静态分配。
3. **浮点运算**：Cortex-M4F/M7 有 FPU 时主要是**FPU 上下文保存**的开销（懒加载会加重中断延迟）；而且浮点运算可能触发库调用，耗时不可预估。
4. **DMA / 总线访问**：不要一边在 ISR 里改已在 DMA 中的缓冲，要么双缓冲，要么在传输完成中断里切换。

**追问链**："那日志怎么打？" → 环形缓冲 + 低优先级任务输出，或者在 ISR 里只记录时间戳和事件码。

**易错**："ISR 里只要短一点就可以 `printf`"——重入问题不是靠短解决的。

## 二、平台与外设（S2 / S4）

### E07：MPU 和 MMU 有什么区别？嵌入式里 MPU 能做什么？

**简历锚点**：S2（STM32 Cortex-M 平台）。所有 Cortex-M 平台都带 MPU，被问到"栈溢出了怎么办"时，**"靠 MPU 加保护"** 是比自己写"哨兵值"更高一档的答案。

**参考回答**：
- **MMU**：地址翻译（虚拟→物理）+ 权限，支持分页，需要页表，开销大；**MCU 一般没有 MMU**，Cortex-M 也没用。
- **MPU**：不做地址翻译，只给"区域"（region）设权限：可读/可写/可执行、特权/非特权、是否可缓存/共享。**典型用法**：
  1. 给任务栈底部设一段不可访问区 → **栈溢出立刻变成 MemManage Fault**，而不是悄悄破坏别的变量；
  2. 把 `.text` 设为只读 → 防止野指针改写代码；
  3. 把外设寄存器区设为特权可访问 → 非特权任务无法乱配外设（RT-Thread 的 `rt_hw_mpu` 一类支持就是这么做的）；
  4. 保护 RTOS 内核对象。
- 一般 8 个 region，且 2 的幂大小、必须对齐，**重叠区域需要靠优先级/sub-region 设计**，配置本身要花时间。

**追问链**："开了 MPU，任务栈大小怎么定？" → 按 [R08](rtos.md#r08) 的水位法估（栈使用率 43%～45% 这种），MPU 只负责"越界立刻发现"，不负责"够不够用"。

**易错**：把 MPU 说成"能防止所有内存错误"——它只能保护**区域边界**，区域内部的越界它看不见。

### E08：Cortex-M 的启动过程、向量表、链接脚本、Bootloader 分别做什么？

**简历锚点**：S2 + S3（Keil AC5 / gcc 两套工具链）+ [W2](/daily/求职准备/简历3.0_全文还原与编号.md) 的 OTA 场景。

**参考回答**：
- **向量表**：`0x0000_0000` 处（或 `VTOR` 指定地址）依次是初始 `MSP` 值、`Reset_Handler`、各异常/外设中断入口。**改 `SCB->VTOR` 就能实现"中断向量重定位"**，这是 Bootloader 跳转应用的关键。
- **链接脚本**（gcc 是 `.ld`，Keil 是 `.sct` / 分散加载）：决定各段放哪个地址、RAM/Flash 多大、栈和堆的起止。
- **Bootloader 跳转 app 前的三件事**：关中断、把 `VTOR` 设成 app 的向量表地址、把 `MSP` 设成 app 的初始 SP，然后跳到 app 的 `Reset_Handler`。**OTA 场景再补两件**：校验升级包（CRC/签名）、写升级标志位（见 [E10](#e10)），否则旧 app 写坏就再也起不来。
- **MAP 文件**是链接后的"地址账本"：确认符号落在哪个段、`_end` 在哪、各段大小多少。

**追问链**："app 为什么必须从固定偏移开始？" → Bootloader 要和 app 各自占不重叠的地址区间，否则跳过去就会踩到自己。

**易错**：说"OTA 就是把固件写进 Flash 就完事"——跳转前的那几步没做，现象就是"写了、重启、还是老版本"。

### E09：Cortex-M 为什么有 HardFault？HardFault 怎么定位？

**简历锚点**：S2 / S6（示波器、逻辑分析仪、故障排查）＋ 实习 IN1 的失效分析口径（现象 → 对照 → 收敛根因，可以作方法论类比，但**别把 IN1 说成 HardFault 排查**）。

**参考回答**：HardFault 是 Cortex-M 的"兜底异常"——**所有没被单独使能的、或触发时优先级不允许的 fault，最后都会变成 HardFault**。常见来源：
- 非法内存访问（空指针、野指针、越界）、非对齐访问（开了对齐检查时）
- 未定义指令、从非法地址跳转（函数指针被破坏）
- 除零（开了 `CCR.DIV_0_TRP`）
- 栈溢出覆盖了返回地址 → 跳到乱地址 → 往往先 HardFault

**定位套路**：在 HardFault 处理函数里保存 **`SCB->CFSR`（fault 状态寄存器）、`HFSR`、`BFAR`/`MMFAR`、以及入栈的 R0–R3, R12, LR, PC, xPSR**（它们按栈帧布局压栈，把栈指针取出来按序打印就能拿到**出错时的 PC**）→ 用 `addr2line` / Keil 的 call stack 换算到源码行 → 再看是哪个变量被破坏。这套"抓现场"的思路和 [W1](/daily/求职准备/简历3.0_全文还原与编号.md) 用 `addr2line` 定位泄漏点是同一类手段。

**追问链**："现场 PC 落在库函数里怎么办？" → 继续看调用栈（LR/帧指针）和栈上的返回地址，或者复现时开 MPU 栈保护缩小范围。

**易错**：说"HardFault 就是指针错了"——它只是**入口**，具体原因要看 `CFSR`。

### E10：OTA 的 Flash 分区、双分区、回滚、升级标志位怎么做？

**简历锚点**：W2（OTA 应用集成：消息队列 + 独立线程、升级前检查网络/电量/堆、mbedTLS + HTTPS、独立 96 KB PSRAM 池）。**这道题是纯原理题**——你的 OTA 走的是 SDK Loader + 手机网络，**没有自己划过分区、没有自己实现回滚**，被问就说"分区和回滚是 SDK Loader 负责的，我只负责前置检查和触发"。

**参考回答**（讲你知道的层次即可）：
- **Flash 分区**：最少要拆成 bootloader 区、app 区、参数区（NVS/配置）、可选的资源区。ESP-IDF 的 partition table 就是这个思路。
- **单分区升级（你这条链路）**：下载到临时区/PSRAM → 校验整包（CRC/签名）→ 写主固件 → 置升级标志 → 重启后在 bootloader 里确认新固件能启动、再清标志。**风险**：写的过程中掉电可能变成"半新半旧"，所以要么写之前备份，要么双区。
- **双分区（A/B）**：升级先写 inactive 分区，验收通过后再把启动指针切过去；失败则还留在旧分区 → 天然的**回滚**能力。代价是 Flash 翻倍、切换逻辑要保证原子（改一个很小的启动选择标志）。
- **升级标志位**：要放在**不易丢失**的介质（NVS/flash RTC 区），带 CRC 和版本号；**写标志必须原子**，或者用"追加式记录 + 取最新有效项"避免写一半坏掉。

**追问链**
- **"升级前为什么要检查电量和可用堆？"** → 你 W2 的答案：≥40% 或外接电源、≥20 KB 可用堆、网络连通，否则升级中途掉电/内存不足会留下不可启动的固件。
- **"TLS 缓冲为什么单独放 96 KB PSRAM 池？"** → 见 [答案稿_04 Q150G](/daily/求职准备/答案稿_04_技能栏与基础题.md)：隔离，别让网络大缓冲挤占 LVGL/UI 堆。
- **"CRC 对了就安全吗？"** → 不对，CRC 只查意外损坏，**真实性要签名**（见 [N09](network-iot.md#n09)）。

**易错**：把 SDK 的 DFU/PAN 流程说成"我设计的双分区回滚"——你的仓库里没有分区表与回滚代码，说了要能立刻打开文件。

### E11：烧录与调试工具链：ST-LINK/DAP-Link、SWD/JTAG、OpenOCD、`addr2line`、ELF 结构

**简历锚点**：S3（Keil MDK + gcc 两套工具链）＋ S6（仪器）＋ W1（用 `addr2line` 定位泄漏点）。

**参考回答**：
- **SWD vs JTAG**：SWD 两根线（SWCLK/SWDIO）+ 可选 SWO，引脚少；JTAG 四根线，支持更多边界扫描功能。Cortex-M 常用 SWD。
- **调试器**：ST-LINK 是 ST 官方，DAP-Link（CMSIS-DAP）是社区/ARM 标准协议实现，J-Link 是商业方案；三者都通过 **SWD/JTAG 访问内核调试单元**。
- **OpenOCD**：开源调试服务端，把 GDB 和探针连起来，负责烧写、断点、读写外设寄存器；配置用 `interface`（探针）+ `target`（芯片）两个文件。
- **`addr2line -e app.elf -f -C 0x0800xxxx`**：把崩溃 PC/日志地址翻译成"文件:行号"，**前提是 ELF 与当时烧录的版本一致**（版本对不上就翻错了，这一点最常被追问）。
- **ELF 结构**：段（`.text/.data/.bss`）+ 符号表 + 调试信息（DWARF）；`.bin` 是纯镜像、没有地址信息，`.hex` 带地址，`.map` 是链接账本。

**追问链**："日志里的地址翻出来是 `??:0`，为什么？" → ELF 版本不对、或者那段地址是库/内联函数被优化掉、或者开了 LTO。

**易错**：说"`addr2line` 能定位泄漏对象"——它只能把人给的地址翻成行号，**泄漏对象是你自己跟踪出来的**（和 [Q037](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md) 里"MAP 看不出动态泄漏"是同一类边界）。

### E12：STM32 的 RCC、时钟树、HSE/HSI/PLL 怎么算？为什么时钟配错外设就出问题？

**简历锚点**：S2（STM32G4/H7）＋ S4（外设驱动）＋ 药箱 D4 里的定时器参数（PSC/ARR）——**一旦定时器/PWM 频率算不对，最先要查的就是时钟源频率**。

**参考回答**：
- **时钟源**：HSE（外部晶振，精度高）/ HSI（内部 RC，便宜但误差大且随温漂）/ LSI（32 kHz，喂 IWDG、RTC）/ LSE（32.768 kHz，RTC）。
- **PLL**：`SYSCLK = f_in × (PLLN / PLLM) / PLLP`（各系列命名略有差异），再经 AHB/APB 分频得到 HCLK、PCLK1/PCLK2。**APB 预分频不为 1 时，定时器时钟会自动 ×2**（这点常被问倒）。
- 定时器频率：`f_tim = f_timclk / ((PSC+1) × (ARR+1))`，例如 D4 的 **PSC=199、ARR=19999**，若定时器时钟是 100 MHz，则 `100 MHz / 200 / 20000 = 25 Hz`——这就是"50 Hz 舵机要算清时钟链"的由来（不同系列主频不同，实际值以工程配置为准，别背错）。
- **时钟不对的症状**：UART 波特率偏移导致乱码、I2C 超时、定时器周期整体偏、ADC 采样率不对。

**追问链**："换了新板子，串口能发不能收、定时器快了一倍，先查什么？" → 依次查 HSE 是否起振（很多板子晶振没起振会 fallback 到 HSI）、APB 分频、`SystemInit` 里的 PLL 参数。

**易错**：把 `PSC`/`ARR` 直接当频率；忘记"`ARR` 计数是 `ARR+1`"（计数从 0 开始）。

### E13：低功耗到底怎么设计？休眠、唤醒源、tickless、功耗怎么测？

**简历锚点**：S2（RTOS 调度）＋ S4（外设）＋ W2 的"升级前检查电量"。项目里**没有功耗实测数据** → 这题按机制答，不要报数字。

**参考回答**：
- **有逐级休眠**：运行 → 睡眠（停 CPU）→ 深睡（停大部分时钟）→ 待机（只剩 RTC/备份域）。**切到深睡态前要保存关键状态**，唤醒后本质上是"复位 + 读唤醒原因"。
- **唤醒源**：EXTI 引脚、RTC 闹钟、低功耗定时器、串口唤醒、无线模块事件。唤醒源要为"没有唤醒源就永远睡着"做好兜底（看门狗/RTC 定时保底唤醒）。
- **RTOS tickless idle**：原来每个 tick 都进 SysTick 中断，空闲时没法深睡；tickless 模式下空闲任务进入休眠，用低功耗定时器补算 tick，醒来后把丢失的 tick 补偿回去——**代价是时间精度与补偿逻辑的复杂度**。
- **平均功耗 ≠ 休眠电流**：要用"运行时间 × 运行电流 + 休眠时间 × 休眠电流"的**在/离比（占空比）**去算；测法用电流表/功耗分析仪看波形积分，或测电池放电曲线。

**追问链**："手表类设备凭什么省电？" → 大部分时间在低功耗态 + 外设按需开 + 高频事件合并（间歇广播/连接事件），而这些的**前提是延迟可接受**（和 [Q105](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md) 连接参数的取舍是同一逻辑）。

**易错**：说"加 `sleep` 就省电了"——不管唤醒源和状态保存，睡了就醒不过来；也不要报一个你没测过的 µA 数。

## 三、网络与应用层（S4）

### E14：TLS 用 ECDHE 握手时，一次完整握手需要几 KB 内存？为什么 MCU 上这么贵？

**简历锚点**：W2（mbedTLS + HTTPS + 96 KB PSRAM 专用池）。[Q126](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md) 只问了"内存开销在哪"，这里补**为什么**。

**参考回答**：
- 开销来自四块：**证书链解析**（服务器证书 + 中间证书，每个都要解析和校验签名）、**握手缓冲**（收发记录层缓冲，最大记录约 16 KB）、**密钥运算**（RSA/ECC 的大数运算与临时缓冲）、**加密上下文**（AES/SHA 的上下文与对称密钥）。
- ECC 比 RSA 省资源（同等安全强度密钥短得多），但**大数运算仍要几百字节到几 KB 的临时空间**，且运算耗 CPU。
- 所以工程上做的是**隔离 + 复用**：TLS 缓冲单独划池（你在 PSRAM 里划 96 KB）、连接尽量长连不反复握手、必要时裁证书链。

**追问链**："为什么不在内部 SRAM 里划？" → SRAM 要留 UI 堆和栈，PSRAM 换的是容量，代价是访问慢；握手是一次性的，慢一点可以接受。

**易错**：说"加密了就不占内存"；把"能连上 HTTPS"等同于"安全"（[Q125](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md)）。

### E15：MQTT 的 QoS、遗嘱、保留消息、会话保持分别解决什么？

**简历锚点**：⚠ **你 3.0 的简历没有写 MQTT**（v2.2 写过，3.0 删了）。所以这题只作**被追问"了解哪些物联网协议"时的知识储备**，答完不要主动说"项目里用了 MQTT"。

**参考回答**：
- **QoS 0/1/2**：最多一次（可能丢）/ 至少一次（可能重复）/ 恰好一次（开销最大）。**"至少一次"要应用层去重**（靠消息 ID）。
- **遗嘱（Will）**：客户端异常断开时 broker 代发消息——用于"设备掉线告警"。
- **保留消息（Retained）**：broker 存最后一条，新订阅者一进来就收到当前状态——适合"设备当前状态"。
- **会话保持（Clean Session = 0）**：断线后 broker 保留订阅关系与离线消息，重连再补发——代价是 broker 要存状态。
- 和 HTTP 比：MQTT 是**长连接 + 发布/订阅**，头部开销小、适合低带宽和弱网；HTTP 是请求-响应，更简单。

**追问链**："设备突然掉电，服务端多久知道？" → 靠 keepalive 超时 + 遗嘱消息。

**易错**：把 QoS 2 说成"可靠所以一定不重复"——它保证的是"恰好一次投递"，实现上要两次往返，**不代表业务幂等**。

### E16：大小端在协议里怎么统一？结构体直接强转解析有什么坑？

**简历锚点**：S4（熟悉 BLE，且 128 位 UUID 是 S4 下的真实项目细节）＋ W4（BLE 分片：偏移、总长、CRC32，[建议加回](/daily/求职准备/简历3.0_全文还原与编号.md)）。

**参考回答**：**统一用网络序或协议约定序**，收发两端都按字段手工编解码：

```c
static uint32_t rd_u32_le(const uint8_t *p) {
    return (uint32_t)p[0] | ((uint32_t)p[1] << 8) |
           ((uint32_t)p[2] << 16) | ((uint32_t)p[3] << 24);
}
```

- **不要 `*(uint32_t *)buf` 强转**：一是字节序跟机器走，二是**对齐**——非对齐地址读 32 位可能直接 HardFault（[E09](#e09)）。
- **结构体直接映射**：只有在"双方都用同一工具链、同一 `packed`、同一字节序"时才安全，跨平台/跨语言一律手写编解码。
- **反向例子**：手表自定义服务的基础 UUID 是 `2D6A5000-...`，但源码里 128 位 UUID 数组**按小端字节存**，照抄进手机端就搜不到服务——这就是"字节序在真实项目里的坑"。

**追问链**："用联合体（union）判断大小端行不行？" → 可以，写一个字节读另一个字节；但**更稳的做法是编译期断言 + 显式编解码**，不要依赖隐式行为。

**易错**：说"Cortex-M 是小端所以不用管"——决定字节序的是**协议**，不是本地机器。

---

### E17：CRC 和校验和怎么选？CRC32、CRC16、累加和分别适合什么？

**简历锚点**：W4（封面分片 CRC32）＋ W2（升级清单）+ [Q128](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md)。

**参考回答**：
- **累加和/异或和**：最便宜，检错能力弱（两个互相抵消的错误查不出来），适合"粗筛"和不那么重要的通信。
- **CRC16**：查 1 位、2 位、突发错误能力强，适合短帧（Modbus、BLE 部分场景）。
- **CRC32**：适合大块数据（固件包、图片整包），误判概率低；**硬件 CRC 外设**（不少 MCU 自带）比分片算更快。
- 三个要点：**多项式/初值/反射/异或输出要两端一致**（否则算出来的值对不上，这是最常见的联调坑）；**CRC 只防意外损坏**（[Q128](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md)）；分片传输要**先总长后 CRC**（[Q150F](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md)）。

**追问链**："为什么手表封面协议要同时有偏移、总长、CRC32？" → 偏移定位、总长判完整、CRC 判内容；三者职责不同（这是你在 Q150F 已经准备过的答案，这里只补"CRC 选型"这一层）。

**易错**：说"CRC32 比 CRC16 更安全"（查的是误码，不是防篡改）；两端 CRC 参数不一致时又怀疑"芯片坏了"。

## 四、Linux 相关（E2 课程 / 实习环境）

### E18 ⚠：Linux 下的 C 程序从源码到运行，中间经历了什么？GCC 的 `-O`、`-g` 怎么选？

**简历锚点**：⚠ E2（课程）＋ S3（gcc、Makefile）。被问到"你 Linux 学到什么程度"时，这是最安全的证明题。

**参考回答**：
`预处理（.i）→ 编译（.s）→ 汇编（.o）→ 链接（可执行 ELF）`，对应 `gcc -E / -S / -c / 链接`。
- **静态库 vs 动态库**：`.a` 在链接期把目标文件拷进可执行文件；`.so` 运行时由动态链接器加载，可共用、可热更新，但**要保证 ABI 兼容**、部署时要能找得到（`LD_LIBRARY_PATH`/`rpath`/`ld.so.cache`）。
- **`-O2` 对调试的影响**：变量被优化掉、行号对不上、函数被内联 —— 所以调试版常用 `-O0 -g`，性能版用 `-O2`；**定位偶发崩溃时用优化版复现、用带 `-g` 的同一构建去查**，别在两个构建之间比较。
- **`-Wall -Wextra -Werror`**：把常见错误升级成工程规范；MCU 侧同理。

**追问链**："`undefined reference` 是哪一步的错误？" → 链接期：函数**声明**在头文件里有了，但**定义**所在的 `.o`/`.a` 没被链接进来或顺序不对（静态库顺序对链接有影响）。

**易错**：说"gcc 一次就编译出可执行文件所以没有中间过程"；把"编译通过"当"程序没问题"。

---

### E19：进程、线程、系统调用、设备文件、`/proc` 这些词，MCU 工程师该怎么答？

**简历锚点**：⚠ E2（Linux 课程）＋ S3（WSL2 开发）。面试官常拿"MCU 的裸机/RTOS 与 Linux 有什么不同"来测你的**系统观**。

**参考回答**（能讲清对比就够）：
- **MCU 上**：没有 MMU/地址空间隔离，任务共享同一地址空间，栈独立、堆常共享；一个野指针可以毁掉整个系统。
- **Linux**：进程有独立虚拟地址空间，线程共享地址空间；用户态通过**系统调用**（`open/read/write/ioctl/mmap`）进入内核态访问硬件和文件。
- **设备文件**：Linux 把设备当文件（`/dev/ttyS0`、`/dev/i2c-1`），应用层用 `open + ioctl` 就能操作串口/I2C —— 这就是"嵌入式 Linux 和 MCU 最大的不同：硬件被抽象成文件"。
- **`/proc`、`/sys`**：内核暴露的运行时信息（进程表、`/proc/interrupts` 看中断统计、`/sys/class/...` 看设备），排查"中断到底有没有来"时很有用。
- **真实工程对应**：泰山派（[上板实战](/embedded-linux/taishan-pi.md)）上的 `systemctl`、串口登录、交叉编译、`findmnt` 这些，就是 [L01–L08](linux-basics.md) 里覆盖的部分。

**追问链**："RTOS 和 Linux 桌面/服务器最大的区别在哪？" → **实时性**：RTOS 调度器可预测、中断延迟确定；通用 Linux 为吞吐优化，实时要靠 RT-Preempt/Xenomai 等专门方案。

**易错**：把 MCU 的"任务"直接叫"进程"；说"它们在 Linux 里也一样"，会被抓"地址空间隔离"这一点。

## 五、工具链与工程（S3 / S6 / S7）

### E20：交叉编译的环境变量、工具链前缀、Sysroot、静态/动态链接分别怎么处理？

**简历锚点**：S3（VS Code + WSL2 交叉编译、CMake、Keil、Makefile、gcc）。[Q143](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md) 问了前缀，这里补环境变量与产物排查。

**参考回答**：
- **`CROSS_COMPILE`**：Makefile 里常写成 `CROSS_COMPILE = arm-none-eabi-`，再拼成 `$(CROSS_COMPILE)gcc`；**ESP-IDF 是 `export.sh` 把工具链目录加进 `PATH`，CMake 用 `CMAKE_TOOLCHAIN_FILE` 指工具链描述文件**（[Q141](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md) 的口径）。
- **前缀**：`arm-none-eabi-`（裸机，无 OS）、`arm-linux-gnueabihf-`（Linux + 硬件浮点 ABI）、`aarch64-linux-gnu-`（64 位）。**用错前缀的表现**：库的 ABI 不匹配，`cannot find -lc` 或运行时 `Illegal instruction`。
- **Sysroot**：交叉工具链的"目标系统根目录"抽象，提供目标板上的头文件和库，编译时以 `--sysroot=` 传入；**找不到头文件时先查 sysroot，再查 `-I`**。
- **静态 vs 动态**：`-static` 把依赖全打进去，部署简单、体积大，适合小资源板；动态链接体积小、可升级库，但部署时要保证 `.so` 存在且 ABI 对得上。
- **构建产物**：`-march/-mcpu/-mthumb/-mfpu` 必须与目标内核匹配（Cortex-M4 用 `-mcpu=cortex-m4 -mfpu=fpv4-sp-d16 -mfloat-abi=hard`），否则硬浮点/软浮点混用会出奇怪问题。

**追问链**："`No such file or directory` 但文件明明在？" → 常见是**动态链接器路径不存在**（换板子/换 libc 后 ELF 的 interpreter 路径对不上），用 `file` / `readelf -l` 看 interpreter，用 `ldd` 看依赖。

**易错**：只说"装了工具链在 `PATH` 里"；把 SCons/CMake/Keil 三套构建的口径混着讲（统一口径照 [Q141](/daily/求职准备/面试拷打_03_拷打题库_技能与基础.md)）。
