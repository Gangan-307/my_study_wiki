# 泰山派上板实战

## 学习目标

把泰山派作为嵌入式 Linux 实验平台，而不是只当一台小电脑使用。完成“串口可救援、网络可开发、环境可复现、外设可验证、系统可重构”的基本闭环。

> 本页不替代官方文档。板卡硬件版本、镜像、SDK、引脚定义、串口参数和烧录工具必须以购买型号对应的官方资料为准。

## 一、这块板在当前阶段怎么用

你已有 ESP32/STM32 基础，泰山派首两个月主要承担四个角色：

1. ARM64 Linux 应用的运行目标机。
2. 串口启动日志、SSH、文件系统和系统服务实验平台。
3. GPIO/I2C/SPI 以及设备树、内核模块的上板验证平台。
4. Buildroot/官方 SDK 生成镜像的启动平台。

编译 Buildroot、U-Boot 和 Kernel 主要放在 WSL 主机完成。对这条学习路线而言，`2 GB + 16 GB` 足够；更大内存和 eMMC 容量主要改善板上编译、多服务并行、桌面/容器和本地数据空间，不会改变 RK3566 的 CPU 能力。

## 三、首次上电前

- [ ] 检查板卡是否有补焊、短路、腐蚀、接口松动或异常气味。
- [ ] 使用官方要求的稳定电源，不通过不明质量的串口模块给整板供电。
- [ ] 确认 USB-TTL 是正确电平，GND 共地，适配器 TX 接板端 RX、RX 接板端 TX。
- [ ] 确认调试串口和波特率；Rockchip 板卡常见特殊高速波特率，但不得猜测。
- [ ] 准备官方恢复镜像和烧录方式，再开始修改启动相关分区。
- [ ] 首次启动先不接自制外设，减少变量。

## 四、保存完整启动日志

串口工具应从上电前开始记录原始文本，不要只截图最后几行。日志文件命名建议：

```text
YYYY-MM-DD_board-hw_image-version_cold-boot.log
```

在日志中标注：

- [ ] U-Boot 及其前置阶段版本。
- [ ] 内存识别结果和启动介质。
- [ ] Kernel version、Machine model、command line。
- [ ] DTB、根文件系统、init 和登录服务。
- [ ] error、fail、timeout、defer 等异常关键词。
- [ ] 从上电到登录可用的时间。

串口是修改网络、设备树或启动配置后的主要救援通道。SSH 能登录不能替代串口。

## 五、运行时基线采集

登录后执行并保存输出：

```bash
date -Iseconds
cat /etc/os-release
uname -a
cat /proc/cmdline

lscpu
grep -E 'MemTotal|MemAvailable' /proc/meminfo
free -h

lsblk -o NAME,MAJ:MIN,SIZE,FSTYPE,LABEL,PARTLABEL,MOUNTPOINTS,MODEL
df -hT
findmnt /

ip -br address
ip route
ss -lntup

tr -d '\0' </proc/device-tree/model; echo
tr '\0' '\n' </proc/device-tree/compatible

dmesg > dmesg-first-boot.txt
```

### 如何核对内存容量

- 4 GB 版本在 `free -h` 中通常不会显示完整 `4.0 GiB`，因为十进制 GB、二进制 GiB、固件及硬件保留区会造成差异。
- 重点看 `/proc/meminfo` 的 `MemTotal`，并与同型号官方正常值比较；约 2 GB 与约 4 GB 的差距足够明显。
- `free` 显示的是 Linux 可管理内存，不是通过芯片封装丝印直接推算的理论容量。
- 若卖家声称自行升级内存，还要冷启动、多轮内存压力测试并检查日志是否有内存错误，单次识别出容量不代表长期稳定。

### 如何核对 eMMC 与 TF 卡

使用 `lsblk`、`blkid`、`findmnt` 和 `/sys/block/<device>/device/` 信息综合判断。设备编号可能因启动方式变化，不要记忆“mmcblk0 永远是 eMMC”。容量显示略低于标称值通常来自十进制/二进制单位和分区开销。

TF 卡可以作为数据盘、实验根文件系统或可回退启动介质，具体能否直接从 TF 启动取决于板卡启动设计和镜像布局。它不能自动等价替代板载 eMMC 中的早期引导内容。

## 六、建立 WSL 到板卡的开发链路

### 网络确认

```bash
# 板端
ip -br address
ip route
ss -lntp | grep ':22'

# WSL
ping -c 4 <board-ip>
ssh <user>@<board-ip>
```

若 WSL 与板卡不通，要区分 Windows 防火墙、WSL 网络模式、路由、板端 SSH 服务和物理网络问题。先测试 Windows 主机与板卡，再测试 WSL，避免一次排查五层。

### SSH 密钥与文件传输

```bash
# WSL 生成专用开发密钥；已有合适密钥时无需重复生成
ssh-keygen -t ed25519 -C "taishan-study"
ssh-copy-id <user>@<board-ip>

scp ./app <user>@<board-ip>:/tmp/
ssh <user>@<board-ip> /tmp/app
```

不要把私钥复制到板卡或提交仓库。初期将测试程序放到 `/tmp`，确认无误后再通过安装脚本或 Buildroot package 部署到固定位置。

## 七、五级上板实验

### Level 1：系统观察

- [ ] 完成板卡档案、启动日志和运行时基线。
- [ ] 找到 CPU、内存、存储、温度、网络和设备树信息来源。
- [ ] 能从串口恢复 SSH 配置错误。

### Level 2：应用开发

- [ ] WSL 交叉编译 ARM64 程序并通过 SCP 运行。
- [ ] 使用 `gdbserver` + `gdb-multiarch` 远程断点调试。
- [ ] 使用 `strace` 定位一次文件、权限或动态库问题。

### Level 3：用户态外设

- [ ] 对照原理图和 pinmux 确认一个安全 GPIO，使用 libgpiod 读写。
- [ ] 通过 I2C 读取一个已知传感器的芯片 ID，逻辑分析仪验证总线。
- [ ] 使用 `termios` 与 ESP32 进行带帧格式的串口通信。

### Level 4：内核与设备树

- [ ] 反编译运行中的 DTB，追踪一个真实设备节点。
- [ ] 构建并加载与当前内核匹配的模块。
- [ ] 修改一个可安全验证的设备树属性，保留前后 diff 和恢复过程。

### Level 5：系统构建

- [ ] 复现官方 SDK 构建。
- [ ] 用 Buildroot 将自己的应用和启动服务加入 RootFS。
- [ ] 在可回退介质上启动自定义系统并完成基本回归测试。

## 八、3.1 寸屏如何安排

显示屏可用于后续学习 DRM/KMS、Framebuffer、触摸输入或 LVGL Linux 后端，但不应占用前四周主线。首轮只完成：

- [ ] 核对屏幕具体型号、接口、电压和对应官方适配说明。
- [ ] 使用官方镜像验证显示和触摸硬件正常。
- [ ] 保存相关 DTS 节点、驱动日志和设备节点信息。

等系统编程、启动链和设备树打通后，再把网关项目状态页显示到屏幕上。这样屏幕会成为项目功能，而不是单独点亮一次的 demo。

## 九、稳定性与安全

### 基础压力观察

```bash
uptime
free -h
cat /sys/class/thermal/thermal_zone0/temp 2>/dev/null
dmesg -w
```

若镜像提供 `stress-ng` 或 memtester，可按板卡散热和官方建议做受控测试，同时观察温度、供电和内核日志。不要在散热条件不明时长时间满载。

### 写盘前四问

1. 我确认了目标块设备的型号、容量、分区和挂载点吗？
2. 我有当前可用镜像或重要数据备份吗？
3. 我已经实际验证恢复模式能被电脑识别吗？
4. 当前命令来自本硬件版本的官方流程吗？

任一答案为“否”，就先不执行写盘、擦除或修改启动环境操作。
