# 综合项目：ESP32 数据节点与 Linux 边缘网关

## 一、为什么选择这个项目

这个项目把现有 ESP32 客户支持经验和新学的嵌入式 Linux 串成一条完整链路。它比单独的 hello driver 更接近真实产品，也能同时证明协议设计、系统编程、并发、网络、部署和故障定位能力。

项目范围控制在两个月能完成的程度：先用串口打通稳定链路，再选做 Wi-Fi/MQTT 和屏幕，不一开始堆满功能。

## 二、系统架构

```text
传感器/模拟数据
      ↓
ESP32 数据节点
  - 周期采集
  - 帧封装与校验
  - 心跳/版本信息
      ↓ UART（必做）/ TCP（选做）
泰山派 Linux 网关
  - 非阻塞接收与协议解析
  - 有界队列和设备状态机
  - 本地日志/最近数据
  - MQTT 或 TCP 上报
  - 配置、重连、健康状态
      ↓
WSL 上的测试服务/MQTT Broker
  - 接收与显示
  - 故障注入
  - 自动化测试
```

## 三、核心需求

### P0：必须完成

- ESP32 每秒发送一帧温度、计数器、运行时间和状态位。
- Linux 网关使用 C/C++ 接收数据，正确处理半包、粘包、校验失败和超长帧。
- 采集/解析与网络发送解耦，队列有容量上限和溢出策略。
- 网关将数据发送到 WSL TCP 服务或 MQTT Broker。
- ESP32 重启、串口短暂断开、网络断开后，网关不崩溃并能恢复。
- 支持配置文件、分级日志、统计信息和 `SIGTERM` 优雅退出。
- 使用交叉编译部署，并由板端 init 系统管理开机启动。

### P1：完成后加分

- 心跳超时后将设备标记为离线，恢复后重新上线。
- 保存固定数量的最近数据，网络恢复后按策略补发。
- WSL 主机侧单元测试覆盖协议解析、环形缓冲区和状态机。
- 使用 3.1 寸屏显示连接状态、最新数据和错误计数。
- 提供简单 HTTP 状态接口或 Unix domain socket 管理接口。

### 暂不做

- 自建复杂 Web 前端和完整云平台。
- 动态加载任意设备插件。
- 数据库集群、容器编排和复杂加密协议。
- 为已有标准驱动支持的 UART/I2C 硬件重新写内核驱动。

## 四、串口协议

建议使用二进制固定头 + 变长 payload：

```text
SOF(2) | version(1) | type(1) | seq(2) | length(2) | payload(N) | crc16(2)
```

设计时明确：

- 多字节字段采用哪种字节序。
- `length` 指 payload 长度还是整帧长度，并设置最大值。
- 解析错误后如何重新寻找 SOF，不能一直卡在错误状态。
- 序号回绕、ESP32 重启归零、重复帧和丢帧如何统计。
- CRC 的具体多项式、初值、输入/输出反转和测试向量。
- 协议版本不支持时如何响应或记录。

先在 WSL 使用文件或伪终端测试解析器，再接真实串口。

## 五、Linux 网关模块划分

```text
src/
├── main.c              # 生命周期和模块组装
├── config.c/.h         # 配置加载与校验
├── serial.c/.h         # termios、重连、原始字节接收
├── frame_parser.c/.h   # 无硬件依赖的流式协议解析
├── message_queue.c/.h  # 有界队列与退出语义
├── device_state.c/.h   # 在线状态、序号和错误统计
├── uploader.c/.h       # TCP/MQTT、退避重连
└── log.c/.h            # 统一日志接口
tests/
├── test_frame_parser.c
├── test_message_queue.c
└── fixtures/
```

`frame_parser`、配置校验和状态机应保持与板卡无关，能在 WSL 上快速单元测试。硬件 I/O 通过清晰接口隔离，不为了测试去 Mock 整个 Linux。

## 六、关键工程约束

### 1. 内存与队列

- 对帧长、设备数和队列容量设置硬上限。
- 明确队列满时丢最新、丢最旧还是阻塞，记录丢弃计数。
- 稳态运行路径避免无限增长的链表和日志缓存。

### 2. 线程与退出

- 线程共享状态必须有明确所有权或同步策略。
- 条件变量等待使用 `while` 检查谓词。
- 退出时先发停止信号，再唤醒阻塞线程，等待线程结束，最后释放资源。
- 不使用 `pthread_cancel` 代替正常生命周期设计。

### 3. 网络重连

- 区分 DNS、连接、发送和协议层错误。
- 使用带上限的指数退避，并加入少量随机抖动。
- 断网期间不能高频重试、刷满日志或无限缓存数据。
- 明确“已写入本机 Socket”不等于云端已经业务确认。

### 4. 日志

每条关键日志包含时间、级别、模块和上下文。至少统计：

- 接收帧数、有效帧数、CRC 错误、长度错误和丢帧估计。
- 串口重连次数、网络重连次数、队列峰值和丢弃数。
- 进程启动时间、版本、配置摘要和退出原因。

日志必须轮转或限制容量，避免写满 16 GB eMMC。

## 七、四阶段实施

### 阶段 A：主机侧协议闭环

- [ ] 定义协议文档和 CRC 测试向量。
- [ ] 实现流式解析器。
- [ ] 测试单帧、半帧、多帧、噪声、坏 CRC、超长帧和随机分片。
- [ ] 建立零告警构建和 AddressSanitizer/UndefinedBehaviorSanitizer 测试。

### 阶段 B：ESP32 到泰山派

- [ ] ESP32 发送真实或模拟数据。
- [ ] 网关使用 `termios` 配置串口并持续解析。
- [ ] 使用逻辑分析仪验证波特率、帧数据和异常场景。
- [ ] 拔插 USB 串口或重启 ESP32，网关可以恢复。

### 阶段 C：网关到服务端

- [ ] WSL 实现 TCP 测试服务或部署 Mosquitto。
- [ ] 网关增加 uploader 和有界队列。
- [ ] 断网、服务重启和慢速接收时行为符合设计。
- [ ] 使用 `ss`、`tcpdump`、`strace` 保存一次定位记录。

### 阶段 D：产品化收尾

- [ ] 加入 Buildroot package 和启动服务。
- [ ] 配置、可执行文件、日志和运行数据路径符合 Linux 习惯。
- [ ] 连续运行至少 24 小时并保存 CPU、内存、温度和错误统计。
- [ ] 形成构建、部署、测试、恢复和已知问题文档。

## 八、故障注入清单

- [ ] ESP32 在一帧中途复位。
- [ ] 连续插入随机字节和错误 CRC。
- [ ] 发送声明长度大于上限的恶意帧。
- [ ] 串口断开后以不同设备名重新出现。
- [ ] 网线断开或 Wi-Fi 丢失。
- [ ] 服务端拒绝连接、慢速读取或主动断开。
- [ ] 队列持续满载。
- [ ] 配置文件缺失、权限错误或字段非法。
- [ ] 磁盘空间不足或日志路径不可写。
- [ ] 运行中收到 `SIGTERM`。

每项都记录预期、实际现象、日志证据和是否自动恢复。
